# D003: Subagents

## Goals

1. A reviewer or implementation worker starts with nothing from the session that launches it, so a review stays blind and every slice starts in an empty context window.
2. Subagents run on the model and reasoning effort the user set for the session; only the cross-family reviewer names its own model.
3. A subagent that the workflow continues is resumed whenever the host allows it, so it keeps its context: a reviewer judges the fixes against its own findings, a blocked worker continues with the answer, and a run that stopped finishes instead of starting over.
4. The cross-family reviewer is set up once per user and machine, outside every checkout, so the tools and logins it needs never enter a repository and every clone and linked worktree finds it.

## Spec

This design covers the subagents of the `canon` workflow, meaning the reviewers of the review gate, of code review and of any other blind review and the workers of `canon-implement`, the review snapshots their confirmations diff, and the setup of the cross-family reviewer. Subagents that other skills launch for their own steps, such as a codebase review's angles, research, broad searches or alternative interface designs, follow those skills. What a review assesses, and how its findings are merged, belong to the review gate and code review.

### Launch

- Same-model reviewers, workers, and a cross-family reviewer that runs as a host subagent are new subagents from the host's own tool: the Task tool in Cursor, the Agent tool in Claude Code, multi-agent subagents in Codex. None is a fork of the session. A cross-family reviewer can instead run as a command ([Reviewers](#reviewers)).
- Subagents are launched without a model or effort, so they run on the session's, which the user sets. Only a cross-family reviewer that runs as a host subagent gets a model, the one the reviewer file names. Since every worker runs at the session's effort, `canon-plan` names a plan's slices that carry a `Risk:` line beside its closing command and suggests high reasoning effort for the implementation session.
- In Claude Code a reviewer is a `general-purpose` or custom subagent, since the built-in Explore and Plan agents cannot be resumed. A worker is a general-purpose subagent.
- A gate launches its first-round reviewers in parallel, and code review issues its reviewers together. A reviewer that runs as a host subagent runs in the foreground unless the session has other work to do meanwhile, such as another review; one that runs as a command runs in the background ([Reviewers](#reviewers)), started before the others. While a review's reviewers read, in any round, the session edits nothing in the work tree outside `.canon/`, so each reads what the review snapshot records; it fixes findings once the reports are in. Workers run one at a time, in plan order; work without a plan has no worker.
- The launching session keeps each subagent's id: a reviewer's agent id, or the session id its command reports, in its review files ([D001§review-files: review files](D001-skill-telemetry.md#review-files)), and a worker's agent id in `.canon/canon-implement/<P id>/S<n>-id.txt`.

### Input and reports

- The `canon-blind-review` skill states what every blind review shares: the prompt's rules on reading and writing, its report contract and known-issue rule, launching, the review files and snapshots, stopped runs of reviewers, the manual fallback, the merge baseline, and the confirmation and follow-up rounds with their prompts. The review gate in the `canon` workflow and `canon-code-review` state only what is their own, such as the gate's Target, As-built and Assess lines, merge rules and status, and code review's briefs; `canon-review`'s angle reviewers report as that contract says. The workflow names these skills without a fallback for when one is missing, since the skills are installed together ([D000§goals: goals](D000-project-overview.md#goals)).
- A reviewer's only input is its prompt, which names files in the repository for it to read: the review gate's reviewer prompt in the `canon` workflow, or the `canon-blind-review` template for every other blind review, a code review's carrying the diff command, the untracked files, the commit list and its sources. It never gets the conversation, a summary of it, or the author's reasoning, worries or expected verdict. On every route the prompt is what forbids it to modify any file, write scratch files or read `.canon/`, and what allows it the project's `canon.py` with `show`, `find`, `which`, `affected` and `check` without `--fix`, which read only, or the files themselves when the host blocks such a call. Every prompt asks for the report in the project's documentation language, which takes precedence over the user's language for the session. A confirmation or follow-up prompt allows in `.canon/` only its diff command, which reads the review snapshots ([Review snapshots](#review-snapshots)); a confirmation prompt needs no `canon.py`, since it names where each fix is.
- The session saves each report of a reviewer that runs as a host subagent, first-round or confirmation, verbatim in that run's findings file, `<role>.md` or `<role>-confirm.md`, never a translation or summary, and merges it in whatever language it came. A run's report is saved once that file is newer than the run's prompt file, which the session writes before launching the run; a notice for a saved report changes nothing, since hosts can repeat a notice or deliver it late. Once the session has no other work, it looks for the report of a run whose notice has not come in the host's record of the run, where [D001§sources: sources](D001-skill-telemetry.md#sources) names one. A reviewer that runs as a command writes its findings file itself, and the session reads it when the command ends.
- A reviewer of a gate or blind review reports every blocker and major finding and at most 10 minor ones, each with its severity and location, then its Questions, and ends with one line, `Verdict: approve` or `Verdict: revise`. A code review reviewer reports findings with severity `blocker`, `major` or `minor`.
- A confirming reviewer answers resolved or not resolved for each finding listed, citing the location that shows it, reports any new blocker the fixes introduce, and ends with a Verdict line. The gate or code review records these answers as [D001§review-dispositions: review dispositions](D001-skill-telemetry.md#review-dispositions) describes.
- A worker's only input is the worker prompt, filled with the plan's path, its slice and the design sections the slice builds on, and followed, for a replacement, by the answer its predecessor was blocked on; the plan carries the rest. The prompt has it build the slice test-first, keep its scratch files in `.canon/canon-implement/<P id>/S<n>/`, edit no plan or design and not commit, and tells it that it cannot reach the user and that search tools which honor `.gitignore` skip `.canon/`.
- A worker stops and reports `blocked` when the plan or a design cannot be followed, naming which and the fix it would propose, or when a decision is needed that the docs and code do not settle; it reports `stuck` when a failing test stays unexplained and its last two attempts produced no new evidence narrowing the cause; otherwise it reports `done`. The report gives the status, the files changed, the tests added with their seams, the test commands run and their results, deviations from the plan and open questions.
- On `done`, the session re-runs the slice's tests and checks that the diff stays within the slice and edits no plan or design.

### Reviewers

- **Same-model reviewer**: a subagent on the session's model and effort. Every gate has one, and code review has two, its Spec and Standards reviewers, each launched the same way.
- **Cross-family reviewer**: the first reviewer that the reviewer file lists for the session's model family and that this host can run. It reviews in the first round of every L2 gate and L2 code review, optionally of an L1 gate, and of any other blind review when the user asks for another family. When its first-round runs stop as [Stopped runs](#resuming-and-replacing) describes, the next reviewer in that list that this host can run takes its place, given the same prompt and the `cross-family` files, and `reviewers` and the dispositions name the reviewer whose report the session merged.
- **Reviewer file**: `$XDG_CONFIG_HOME/canon/reviewer.md` (default `~/.config/canon/reviewer.md`), one per user on the machine, which every checkout reads. Under a heading for each model family the user's sessions run on, it lists, in no fixed syntax, that family's reviewers of another family in fallback order, or `none`, for every host or for one it names; a reviewer listed under no heading, as earlier setups wrote them, serves every family that has no heading, except its own, so a heading the setup writes fully decides its family. Each reviewer has its model and effort, how to run it and what each host needs to run it, such as running outside its sandbox. It runs either as a shell command with `<prompt>` and `<out>` placeholders that starts a new read-only session, leaves the final review in `<out>` and prints its session id where the file says, such as the `session id:` line of `codex exec`, which for an entry that does not say is a line of its output naming the session id, or as a subagent of a named host with a named model, which a session on another host skips. For a command, the session substitutes the cross-family reviewer's prompt and findings files for `<prompt>` and `<out>`, writes the filled prompt to the first, runs the command in the background from the repo root, reads `<out>` when it finishes and writes the session id from the command's output to `<role>-id.txt`, leaving that file empty when it finds none.
- **Migration and writes**: a session that needs the reviewer file and finds none copies there an earlier setup's `.canon/canon-blind-review/reviewer.md` from the current checkout or the main one, and reads that file in place when the copy fails. The file lies outside the workspace, so a sandboxed session writes it with the user's approval; when a setup's write fails, the review takes the manual route.
- **Setup**: the procedure is in the `canon` skill's workflow (Subagents). `canon-init` runs it as one step of setting up a project or alone, and a review that needs the cross-family reviewer runs it before the review, each only when the file gives the session's family neither a reviewer this host can run nor a `none` that covers this host; `canon-init` also runs it when the user names that flow. A review asks only about the session's family, `canon-init` about every family the user says their sessions run on. For each family it shows what the file lists for it, then asks, for each reviewer in order of preference, which tool runs it, an agent CLI, which works from every host, or a subagent of their host with a named model, and its model, suggesting the family's flagship, and its reasoning effort. It builds each command from the tool's `--help`, runs it once on a one-line prompt and fixes it until it works, noting what the host needed and where the command prints its session id. It writes each family it asked about under its heading, its reviewers in the user's order of preference in place of what the file held for it, keeping those only another host can run unless the user drops them, and leaves the other headings and the reviewers under no heading as they are. A family the user has no reviewer of another family for, or declines to set one up for, is written as `none`, for this host alone when the family keeps reviewers another host runs, so the setup does not ask about it again on this host.
- **Manual fallback**: when the reviewer file gives the session's family a `none` that covers this host, the setup could not write the file, or the first-round runs of every reviewer the file lists for the session's family that this host can run fail and are not recovered as [Stopped runs](#resuming-and-replacing) describes, the session tells the user why in one line, naming `canon-init`'s reviewer setup, run by name, when the family has `none`, gives the filled prompt in one code block that any tool able to read the repository can run, and waits for the pasted result. It keeps that prompt and result as the cross-family reviewer's files, without an id, and records the reviewer as `manual:<model>`.

### Resuming and replacing

- **Stopped runs**: a subagent whose run stops before it reports, because the host reports it interrupted, timed out or failed, or its record shows the run ended without a report, gets one more run, as does a reviewer command that exits without writing `<out>`. It is resumed by its id, given only a request to continue where it stopped and end with the report its prompt asks for; when it cannot be resumed, a new one given the same prompt replaces it and starts the work over. A cross-family reviewer that runs as a command cannot be resumed, so a failed command runs once more. When that run stops or fails too, the session stops trying: a worker's slice pauses, with the stopped runs as its problem; a first-round cross-family review moves to the next reviewer the reviewer file lists for the session's family that this host can run, and to the manual route after the last; findings the cross-family reviewer cannot confirm, and its part of a follow-up round, go to the resumed same-model reviewer, as under Confirmation and Follow-up; and a same-model review waits for the user.
- **Confirmation**: after accepted blocker or major findings are fixed, the reviewers that raised them confirm the fixes in one round, given only the confirmation prompt of the `canon-blind-review` skill and what this list adds to it. Before the first round, and again once the fixes are made, the session takes a [review snapshot](#review-snapshots), keeping the first one's id in `snapshot.txt` and the second's in `snapshot-confirm.txt` among the review's files. The confirmation prompt's diff command, `git -C .canon/canon/snapshots diff <first> <second> -- <paths>` with the paths of the files the fixes touched, shows only what the fixes changed, untracked files included, whether or not anything was committed, and the prompt allows that command and nothing else in `.canon/`. The session runs the command first: when a snapshot failed, the first id is lost or the command fails, the prompt says that no diff is available, and the reviewer reads the fixes at the locations it lists. A reviewer that runs as a host subagent, same-model or cross-family, either code review axis included, is resumed by its id: the Task tool's `resume` in Cursor, SendMessage to the agent id in Claude Code, and `send_input` to the agent id in Codex, after `resume_agent` when the agent was closed. A cross-family reviewer that runs as a command, and a reviewer that cannot be resumed, gets a new run of the same reviewer, given the confirmation prompt followed by its first-round findings. A manual-fallback reviewer's findings, and those the cross-family reviewer could not confirm, are confirmed by the resumed same-model reviewer, given the confirmation prompt followed by those findings, named `cross-family:F<n>`; in a code review, each goes to the resumed reviewer of its axis. There is no further round.
- **Follow-up**: a gate's follow-up round ([D007§follow-up-round: follow-up round](D007-change-tiers.md#follow-up-round)) takes a review snapshot once the new revisions are made, keeping its id in the round's own `snapshot.txt`, and gives each of the gate's reviewers the follow-up prompt of the `canon-blind-review` skill. The prompt asks for a review of what changed, reported as in a first round, and its diff command runs from the last snapshot of the gate or its previous round, that round's `snapshot-confirm.txt` or else its `snapshot.txt`, to the new one, over the revised targets; when a snapshot is missing or the command fails, it names the revised sections instead. A reviewer that runs as a host subagent is resumed by its id; a cross-family reviewer that runs as a command, and one that cannot be resumed, gets a new run, given its first-round prompt followed by the follow-up prompt; a manual-fallback reviewer's part goes to the resumed same-model reviewer. Fixes of the round's accepted blocker and major findings are confirmed as above, from the round's own snapshot.
- **Workers**: a worker blocked on a question that the session settles with the `canon-grill` triage is resumed with the answer, and one blocked on a plan problem with one clear fix is resumed after the session edits and logs the plan. A worker that cannot be resumed is replaced by a new one, given the worker prompt followed by the answer when it was blocked on a question. Before a new worker replaces one, the session stashes the slice's changes, new files included, under a message naming the slice and the replacement and logs the stash, so the new worker starts from the slice's start, in the trace unit that [D001§call-sites: call sites](D001-skill-telemetry.md#call-sites) gives it. A question only the user can answer, a plan problem without such a fix, any design problem and a `stuck` report pause the slice; a stuck worker is not retried. A paused slice keeps its changes, new files included, in a stash named after it and its problem in the plan's Log, for whoever resumes it.

### Review snapshots

`canon.py snapshot` records the work tree for a confirmation's diff and prints the snapshot commit's full id, whether tracing is on or off.

```text
.canon/canon/snapshots/.git            review snapshot repository: refs/snapshots/<id> per snapshot
.canon/canon/snapshots/snapshot.lock   held by each call
```

- The repository lives in the checkout's `.canon/canon/snapshots/`, found as [D001§switch-and-storage: switch and storage](D001-skill-telemetry.md#switch-and-storage) finds the trace directory, so a linked worktree has its own; the diff command runs from that checkout's root. It is built on first use as the trace one is, and each call writes `.canon/canon/.gitignore` when it is missing, as `trace start` does. Nothing is written in `.canon/canon/trace/`, so tracing off still writes nothing there.
- It takes the snapshot as [D001§snapshots: snapshots](D001-skill-telemetry.md#snapshots) takes a trace snapshot, with no parent, in this repository instead of the trace one and at `refs/snapshots/<id>`, where `<id>` is the UTC time and 6 random hex digits. The snapshot holds what `git add -A` would record, and the project is left as a trace snapshot leaves it. Step 5 is skipped: each call writes the absolute path of the project's object directory, as `git rev-parse --git-path objects` names it, to the repository's `objects/info/alternates`, so a snapshot stores only the objects the project lacks and the first one copies no tree. A snapshot that reaches an object the project has since pruned no longer diffs, and the repository's `gc --auto` fails, unreported, until that snapshot expires.
- The repository is scratch. Each call, holding `snapshot.lock`, first deletes, best-effort, the refs of snapshots taken more than 30 days ago and the index copies and `.init-<id>` directories that interrupted calls left more than an hour ago; step 6's `gc --auto` reclaims the space once enough packs or loose objects accumulate. Deleting the directory loses only the diffs of open reviews.
- A call that records no snapshot prints `snapshot error: <reason>`, a reason as [D001§event-lines: event lines](D001-skill-telemetry.md#event-lines) defines, with `alternates` and `gitignore` as the steps that write the repository's alternates and `.canon/canon/.gitignore`, followed on standard error by Git's message when there is one, and exits 1: outside Git, when the untracked and unstaged files total more than 10 MiB, after 5 s waiting for `snapshot.lock`, or when a step fails. A project's copy of `canon.py` that predates the command fails with a usage error instead; either failure leaves the confirmation without a diff.

## Decisions

- Subagents are new, never forks of the session: a fork carries the conversation, which would unblind a reviewer and fill a worker's context window (`canon-blind-review`'s definition of a blind reviewer; e71dae1).
- Subagents run on the session's model and effort, which the user sets: in Cursor a Task subagent runs on the session's model unless the user asks for another, from a fixed list whose names fix the effort, so workers and same-model reviewers need no setup (README, Host verification). It replaced per-role effort tables and the Reviewers and Workers lines (3c560ed).
- A confirmation resumes a reviewer that runs as a host subagent, so it judges the fixes against its own findings (3c94281), and reruns a cross-family reviewer that runs as a command with its first-round findings, which needs no per-tool session handling (6ac41ad). Findings whose reviewer cannot confirm them, a manual-fallback reviewer's included, go to the resumed same-model reviewer, so the user relays nothing a second time (`canon-blind-review`).
- A confirmation diffs two snapshots of the work tree, taken before the review and after its fixes: work not yet committed has no commit to diff from, and a `git diff` from HEAD mixes the change under review with its fixes. The gates of D001, P001, P002 and D000 each needed an ad-hoc copy or a full reread instead (2026-10-15 to 2026-10-23), and copies of each reviewed file (r3) needed their own rules for untracked, created and deleted files. The snapshots reuse trace's, which record untracked files and add no file to the project's `.git`, read-only in Codex's sandbox, and live outside the trace directory, which tracing off leaves untouched (2026-10-29).
- Review snapshots borrow the project's objects instead of copying them as trace's do: they serve a review for days, so a checkout's first review need not copy the whole tree, 45 MiB in a 20,000-file checkout ([D001§snapshots: snapshots](D001-skill-telemetry.md#snapshots)), and a snapshot whose objects the project prunes loses only its diff.
- Reports come in the documentation language and are saved verbatim: a user's rule to reply in Simplified Chinese reached the reviewers, and sessions saved translations or summaries whose originals survived only in the subagents' transcripts ([R003: Silk design phase](../reviews/R003-silk-design-phase.md), F4).
- Reviewers run in the foreground when the session has nothing else to do, and a session checks whether a reviewer's report is saved before acting on its notice and looks in the host's record while a notice is overdue: a host delivered a notice again, late, after the session had merged that report, and another sent none for a finished confirmation, so the session idled until the user asked (R003-F12; D001 r8's confirmation, 2026-11-05).
- `canon-blind-review` is the one place for the rules every blind review shares: they were restated in up to four skill files, so one rule change edited three to six of them ([R001: Codebase review of the canon module](../archived/reviews/R001-canon-module.md), F3; b387f60, 869e499, 98ab39c).
- While reviewers read, the session leaves the work tree alone instead of reviewers reading a checkout of the snapshot, which would cost a full checkout per review and lack the history `check` reads: an author edited while a reviewer still read, then counted its approve as covering those edits ([R003§r003-f5-reviewers-read-the-live-work-tree: R003-F5](../reviews/R003-silk-design-phase.md#r003-f5-reviewers-read-the-live-work-tree)). Edits by other sessions sharing the checkout are R003-F14's.
- Reviewers write no scratch files, and workers keep theirs in `.canon/canon-implement/`: a gate reviewer and a code reviewer each left one in the tree under review, and a worker given no place wrote its benchmarks to `/tmp`, where every write waited for the user's approval (2026-10-23).
- The reviewer file lives in the user's config directory, beside the trace switch ([D001§switch-and-storage: switch and storage](D001-skill-telemetry.md#switch-and-storage)), outside every checkout: the tools and logins its reviewers rely on differ between machines but not between checkouts, and a file in each checkout's `.canon/` sent every clone and linked worktree to the manual fallback (6ac41ad; R001-F7; the user's decision, 2026-11-11).
- A missing reviewer is set up from the user's first answer, a family without one is recorded as `none`, and each family lists its reviewers in fallback order: without a file, each L2 gate of a project rediscovered the reviewer from old transcripts or asked the user again, and the setup re-asked in every run of `canon-init` (R003-F3, D004 gate; the user's decision, 2026-11-11). Reviewers are listed per session family because one global order cannot express a preference such as Claude sessions to GPT, GPT to Gemini and Gemini to Claude.
- Codex resumes a subagent with `send_input` to its agent id, and `resume_agent` reopens a closed one (openai/codex 5228d94, `codex-rs/core/src/tools/handlers/multi_agents_spec.rs`).
- A stuck worker's slice pauses for the user instead of being retried: a94fe18 made workers inherit the session's effort, which left no higher effort to retry at.
- A subagent whose run stopped gets one more run, resumed when it can be: a new one starts the work over, as a replaced reviewer did in D002's gate before the user asked for resuming, while the resumed one finished that review (2026-10-22). A second stop ends the attempts, since a stop that repeats, such as a hanging test or a full context, would otherwise loop.
- A replacement worker starts from the slice's start, its predecessor's changes stashed: a half-built tree would give the new worker a wrong baseline for the tests it must keep green.
