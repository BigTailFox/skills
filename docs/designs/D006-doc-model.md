# D006: Doc model and writing rules

## Goals

1. Every engineering doc of a project is one of six numbered types, each with fixed sections, statuses and frontmatter fields, and an id that identifies it for life, so any session or model can find, read and reference it.
2. `canon.py check` enforces the doc model's mechanical rules on the work tree, on what the next commit records or on a commit, and `check --fix` applies the fixes that need no judgment, so agents follow its output instead of re-checking rules by hand.
3. `canon.py new` creates each doc from its type's template with the next free id; `canon.py archive` moves a doc and its attachments to `archived/` and rewrites every link to them, and refuses while the type's terminal conditions fail.
4. Docs state each fact once, in the doc that owns it, for a reader who arrives through a pointer.
5. No session takes in another's uncommitted work: sessions that work at the same time each have a linked worktree and branch, a subagent checks and fixes only the docs it may edit, and a session that commits part of a checkout's changes commits only what it staged, checked as the commit records it.

Out of scope: the generated index and `index --staged` ([D005: Docs index](D005-docs-index.md)); D000, as-built revisions and `as_built`, ids that Git history keeps taken, docs by their name such as READMEs, and unchecked commits and coverage in `audit` ([D002: Project overview and as-built designs](D002-overview-and-as-built.md)); `init`, `adopt`, the `AGENTS.md` block, and the `.gitignore` lines and pre-commit hook `init` writes ([D004: Project setup](D004-project-setup.md)); change tiers, the review gate and design problems ([D007: Change tiers and the review gate](D007-change-tiers.md)); `rename`, `renumber`, `show`, `find`, `which` and `affected` ([D010: Doc queries and renames](D010-doc-queries-and-renames.md)); the rest of `audit` apart from the idle docs it skips ([Statuses and archiving](#statuses-and-archiving)), which no design covers.

## Spec

The agent-facing text of this spec is the `canon` skill: `SKILL.md` (Layout, Doc types, Frontmatter, Rules, and the Tool table's rows for `check`, `new`, `status` and `archive`), `doc-types.md`, `writing.md` and the experiments of `workflow.md`'s docs step 5 in `skills/governance/canon/`, and `canon-design`'s Gate step 4, which sets a concept the design absorbed to `adopted` and an experiment the design links to `concluded` ([Doc types](#doc-types)).

### Layout

- A project is a directory holding an `AGENTS.md` that Git tracks or would add, other than an installed skill file ([D002§installed-skills: installed skills](D002-overview-and-as-built.md#installed-skills)); outside Git, one found while walking the tree, skipping directories named `node_modules` or `venv` or starting with `.`. Its docs root is its `docs/` directory, when that exists. Repo-wide and cross-module docs live in the repo root's `docs/`, a module's docs in the module's `docs/`; a more specific `AGENTS.md` and its `docs/` govern their subtree and override broader rules.
- The repo root is the top of the Git work tree, from whichever of its directories a command runs, else the directory the command runs in. `check` reads the files Git tracks or would add that exist on disk, or outside Git the files that walk finds; under `--staged` or `--rev`, the files of the tree it checks ([check](#check)).
- A docs root holds:

  ```text
  docs/
  ├── README.md                  the index (D005)
  ├── concepts/  designs/  plans/  reviews/  experiments/  investigations/
  │   ├── <id>-<slug>.md         a numbered doc of the directory's type
  │   └── <id>/                  its attachments
  ├── guides/                    unnumbered docs for users and operators
  ├── assets/                    images and files shared by several docs or guides
  └── archived/                  README.md (D005) and the six type directories, for docs in a terminal status
  ```

- Attachments of a numbered doc (data, scripts, reports, prototypes, images used only by it) live in `<type directory>/<id>/` beside the doc. The directory is created with the first attachment; large binaries are linked, not committed. `archive` moves the directory with its doc.
- Guides explain how to use the system and link to designs for specs. Only link checks apply to the `.md` files under `guides/` and `assets/` and in attachment directories.
- Readers skip `archived/` unless researching history.
- Temporary files of canon skills (prompts, scratch prototypes, handoffs) go in `.canon/<skill>/<topic>/` at the repo root, `<topic>` a short kebab-case slug, never in the OS temp directory or the tracked tree. Nothing there is a doc: what is worth keeping becomes an attachment or doc content. `.canon/canon/trace/` is not scratch ([D001§switch-and-storage: switch and storage](D001-skill-telemetry.md#switch-and-storage)), and `new` keeps its id lock at `.canon/id.lock` ([Templates and `new`](#templates-and-new)).
- The linked worktrees of sessions that work at the same time go in `.worktrees/<branch>/` at the repo root ([Concurrent work](#concurrent-work)), which Git ignores as it does `.canon/` ([D004§init: init](D004-project-setup.md#init)).

`check` errors on entries that do not fit:

- an entry directly in `docs/` or `docs/archived/` other than those above, `guides/` and `assets/` being allowed only outside `archived/`, once per entry: `ERROR <entry path>: unknown entry; allowed: README.md, archived/, guides/, assets/, concepts/, designs/, plans/, reviews/, experiments/, investigations/`, the list inside `archived/` being `README.md` and the six type directories. The message ends with the next step, `TYPE` and `FILE` printed as they stand:
  - for a file named `<id>-<slug>.md` or a directory named `<id>` ([Ids and file names](#ids-and-file-names)): `; move it into <type directory>/`, with the directory of the id's type, prefixed `archived/` inside `archived/`;
  - for any other entry inside `archived/`: `; move it out of archived/`;
  - outside `archived/`, for a file ending in `.md`: ``; adopt it with `canon.py adopt <entry path> TYPE` or move it into guides/``; for a directory holding such a file at any depth: ``; adopt its .md files with `canon.py adopt FILE TYPE` or move it into guides/``; for any other entry: `; move it into guides/ or assets/`;
- a file in a type directory that is neither a doc file of that type ([Ids and file names](#ids-and-file-names)) nor inside a directory named like an id of that type: `ERROR <path>: invalid doc path; expected designs/DNNN-kebab-slug.md (D may add one A-Z suffix)`, naming the type's directory and letter, the suffix note for designs only;
- a file in an attachment directory whose id no doc has in the same docs root and the same live or archived part: `ERROR <path>: attachment directory <id> has no matching doc beside it`, once per file.

### Ids and file names

- An id is a type letter (`C`, `D`, `P`, `R`, `E`, `I`), a number of at least 3 digits, zero-padded to 3 and with no other leading zero (`D012`, `D1000`, never `D0012`), and for a sub-design one letter `A` to `Z` (`D012A`).
- A doc's file is `<id>-<slug>.md` in its type's directory, the slug kebab-case (`[a-z0-9]+(-[a-z0-9]+)*`). Its title is its only H1, `# <id>: <title>`.
- The kebab form of a text is the text lowercased, each run of characters other than `a-z` and `0-9` replaced by one `-`, trimmed of `-`, and `doc` when nothing is left.
- Ids are unique across the repository, over every docs root and archived docs included. The id is a doc's identity: docs are created with `new`, retired with `archive`, and given a new slug with `rename`; a doc is never deleted and an id never reused.
- A new doc's number is one above the highest of its type among the docs of every docs root, archived docs and sub-designs included, and the ids history keeps taken ([D002§project-overview-d000: D000](D002-overview-and-as-built.md#project-overview-d000)). A sub-design gets the first letter, from `A`, not taken the same way.
- Sub-designs have one level. `check` errors with `sub-design needs parent D012` when no doc, archived included, has the parent's id.
- `new` and `archive` exit with `canon: unknown document <id>` for an id argument no doc has, and `canon: <id> is the id of <path> and <path>; renumber one of them first` for one several docs have.

`check` errors:

- on each doc whose id an earlier doc has: ``duplicate id <id>, also <path>; run `canon.py renumber <path> --base <ref>` on the doc this branch added, with the branch it merged or rebased onto``;
- with `--base REF`, on each doc whose id exists in REF's tree but not at the merge base of REF with HEAD, or with REV under `--rev`: ``<id> was also added on <REF> as <path in REF>; run `canon.py renumber <path> --base <REF>` ``;
- in a Git checkout, on each doc file deleted, not renamed as Git's rename detection pairs it, whose id no doc of the tree checked ([check](#check)) has: between HEAD, when there is one, and the work tree, or the staged tree under `--staged`; under `--rev`, between REV's parent and REV when REV has exactly one parent; and, with `--base`, on the branch since the merge base, up to HEAD or REV: `<id> was deleted; restore it and archive it instead`, except for a design that owned `architecture` ([D002§project-overview-d000: D000](D002-overview-and-as-built.md#project-overview-d000)).

### Doc types

| Type | Directory | Required sections | Statuses, terminal ones last |
|---|---|---|---|
| C concepts | `concepts/` | Motivation, Ideas, Open questions | draft → adopted, dropped |
| D designs | `designs/` | Goals, Spec, Decisions | draft → accepted → active → superseded, retired |
| P plans | `plans/` | Current state, Slices, Notes, Log | draft → accepted → in-progress → done, abandoned |
| R reviews | `reviews/` | Scope, Findings | open → closed |
| E experiments | `experiments/` | Question, Setup, Results, Conclusion | planned → running → answered → concluded, superseded, overturned, dropped |
| I investigations | `investigations/` | Symptom, Reproduction, Analysis, Resolution | open → resolved |

A doc may add other sections. `check` errors with ``missing section `## <name>` `` for each required `## ` heading, matched by its exact text in any order, and with ``body must have exactly one H1 reading `# <id>: <title>` `` unless the body outside code fences has one H1 and its text is `<id>: ` and a title.

- **Concepts**: ideas, trade-offs and brainstorming, with no spec and no plan. A concept keeps Motivation, Ideas and Open questions and adds or orders other sections as its ideas need; the rules of the design sections below (Goals, Spec, Budgets, Decisions, Known issues) do not bind it. When an idea becomes work, a design that links the concept is created or revised, and once designs have absorbed all of the concept, the concept is set to `adopted` with `status` or by editing the field; a concept whose other Ideas still wait, such as a module's backlog, stays `draft`. A concept is not revised to follow the designs that absorb its Ideas, and an adopted one stays live; where it and a design differ, the design holds. `adopted`, like an experiment's `concluded`, is valid both outside and inside `archived/`: `archive <id> adopted` archives a concept when the user judges that it no longer informs any work. A rejected concept is archived as `dropped`.
- **Designs**: one per topic, revised in place for the topic's whole life, and the source of truth: where a plan or a concept disagrees, the design wins.
  - Goals: what the design must achieve, measurable where possible. Spec: the authoritative, precise specification of every topic in `owns`, interfaces given as code (signatures, schemas, CLI usage, config keys); user-visible behavior is specified here. Budgets, only when there are quantitative targets: each target with how it is measured; a target whose number needs a first measurement states what is measured and how, and takes its number from that measurement. Decisions: one line per key decision with its reason. Known issues: [below](#known-issues-findings-and-slices).
  - Status: `draft` until the review gate makes it `accepted` ([D007§gate-status: gate status](D007-change-tiers.md#gate-status)); `active` with `implemented` once an implementation has landed, or a revision that needs no code change has passed as that section states, and still `active` while a revision's spec leads the code. Archived as `superseded`, with the successor in `refs`, or `retired` when the feature is removed. An as-built revision's status: [D002§as-built-revisions: as-built](D002-overview-and-as-built.md#as-built-revisions).
  - Split: a design that outgrows one doc gets sub-designs with `new D <slug> --parent D012`; the sub-topic's spec, `owns` and `paths` move into the sub-design, and the parent keeps the overview and links its children. A sub-design that outgrows itself becomes a new top-level design. Whenever a topic moves to another design, by a split or otherwise, these move together: its spec, its `owns` entries, the `paths` entries no topic left behind governs, and its known issues, renumbered to the new design's ids with Source and Since kept and every citation of the old ids updated. Each restatement left behind, in the old design or elsewhere, becomes a link.
- **Plans**: the implementation plan and log of one change, created only from an accepted or active design, with `new P <slug> --from D012`; `new` refuses a plan without `--from` ([Templates and `new`](#templates-and-new)). An existing plan that `adopt` turns into a doc ([D004§adopt: adopt](D004-project-setup.md#adopt)) gets its `based_on`, `refs` and link to its design by hand.
  - Current state, at the top: the current slice, the next action and paused slices with their reasons, updated at the end of every slice; a new session resumes from it.
  - Slices: ordered `### S1: <name>` subsections. Each starts with a `Status:` line, then a `Risk:` line naming the kinds when the slice involves complex logic, concurrency, performance, security or data migration (`Risk: concurrency, data migration`), then lists its changes and the test criteria that prove it done. Each criterion names its seam, the public interface the design's Spec defines where the test observes behavior; an accepted plan's seams are agreed with the user, and tests go only there.
  - Notes: risks and constraints for the implementer, findings about the plan the user left for later, and details the plan settled that its design leaves unstated, which the docs step writes into the design with the experiment links they carry. Log: decisions, results, evidence and deviations, appended as they happen.
  - Status: `accepted` after the review gate ([D007§gate-status: gate status](D007-change-tiers.md#gate-status)), `in-progress` while implementing. Archived as `done` once every slice is `done`, in the commit that completes the implementation, or as `abandoned`.
- **Reviews**: findings of a review of code, modules, the whole repo or a concept. Scope states what was reviewed, at which commit and from which angles (function, performance, security, architecture, usability). A periodic review or a concept review produces one R doc per run, its reports in `reviews/<id>/`. A concept review runs the `canon-blind-review` skill with its template for artifacts outside the review gate; its Scope names the concept revision it read, and its findings link the doc that owns each spec instead of restating it. Code review of a change and the review gate produce no R doc. Archived as `closed` as soon as no finding is `open`.
- **Experiments**: one question answered with evidence, by a run (benchmark, prototype, measurement) or by research of primary sources (official docs, specs, source code). A later run that answers the same question, such as a measurement after research, extends the experiment's Setup and Results while it is `planned` or `running`, or `answered` and cited by no live doc ([Statuses and archiving](#statuses-and-archiving)), which moves back to `running` for the run; otherwise the run gets a new experiment that links it. A new question is a new experiment. Setup lists `- Commit:`, `- Environment:` and `- Command:` for a run, so it can be rerun, and `- Sources:` for research, one primary source per indented line. Results link every measurement to its raw data and every finding to its source. Raw data and source excerpts go in the experiment's attachment directory ([D008§research-brief: research brief](D008-experiments.md#research-brief) for excerpts), prototype code where [D008§prototype-files: prototype files](D008-experiments.md#prototype-files) puts it. The conclusion is absorbed as [D008§absorbing-a-conclusion: absorbing a conclusion](D008-experiments.md#absorbing-a-conclusion) states.
  - Status: `running` while a run or research is under way; `answered` once the Conclusion is written, until a design or plan absorbs it; then `concluded`, which means answered and absorbed: `status` sets it only while the body of a live design or plan links the experiment ([Statuses and archiving](#statuses-and-archiving)). The session that links an experiment for its conclusion sets it `concluded` ([D008§absorbing-a-conclusion: absorbing a conclusion](D008-experiments.md#absorbing-a-conclusion)); else `canon-design`'s Gate step 4 does for each answered experiment its design links, and the docs step for each one the change's designs and plans link, before it archives any plan. Whichever step sets an experiment `concluded` also archives each live answered or concluded experiment that the newly concluded one links on the same question: when the earlier result still holds, it first moves to the new experiment the links of live designs and plans that cite the earlier one, then archives that one as `superseded`; when the new result shows it wrong, it archives it as `overturned`. A concluded experiment stays live while a live doc cites it ([Statuses and archiving](#statuses-and-archiving)). It is archived as `concluded` once none does, which the docs step does for each that `check` reports uncited ([check](#check)), such as one only a plan it archived linked; as `superseded`, with its successor in `refs`, when a later experiment answers its question in its place and its result still holds; as `overturned` when its result is found wrong, its Conclusion stating what was wrong and linking the experiment or doc that showed it; and as `dropped`, from any status, when its question no longer matters, its Conclusion saying why. The session that finds an experiment's result wrong archives it as `overturned`, treats each accepted or active design that links it as a design problem ([D007§design-problems: design problems](D007-change-tiers.md#design-problems)), revises a draft design it is writing that links it, and names to the user each other live doc whose body links it, such as a draft design, a plan or a later experiment.
- **Investigations**: debugging and profiling. Reproduction lists `- Commit:`, `- Environment:` and `- Command:`; repro scripts and captured logs or traces go in `investigations/<id>/`, secrets replaced by `<REDACTED>`. Resolution lists `- Root cause:`, `- Fix:` and `- Verification:`, all filled before archiving. Archived as `resolved` as soon as the defect is fixed or verified not to be one; a root cause that exposes a spec gap gets the design fixed too.

### Statuses and archiving

- `check` errors with ``status `<status>` invalid; use one of <the type's statuses>`` for a status outside the type's, a missing `status` giving only the missing-field error ([Frontmatter](#frontmatter)), with ``status `<status>` requires the doc to be in archived/; use `canon.py archive` `` for a terminal status outside `archived/`, and with ``status `<status>` requires the doc to be outside archived/; set one of <the type's terminal statuses>`` for another status inside it; a concept's `adopted` and an experiment's `concluded` are valid in both places ([Doc types](#doc-types)).
- A non-terminal status, a live concept's `adopted` and a live experiment's `concluded` are set with `status` or by editing the field; `archive` sets every other terminal status, and no command moves a doc back out of `archived/`.
- A live concluded experiment is finished work: `audit` leaves it out of the open docs it reports as idle, as it leaves out concepts and active designs.
- A live design or plan links an experiment when the body of a design or plan outside `archived/`, in any docs root, links the experiment's file, with or without an anchor; a link into its attachment directory does not count. `status` sets `concluded` only for an experiment so linked.
- A live doc cites an experiment when the body of a numbered doc of any type outside `archived/`, other than the experiment itself, links it as above and that doc is not a concluded experiment, or when a chain of such links reaches it from one: a link from a concluded experiment counts only while a live doc cites that experiment, so concluded experiments that link only one another cite nothing. A cited concluded experiment is not archived as `concluded`, and `check` reports one that is ([check](#check)); a later run does not extend a cited answered one. The `<ids>` of `archive`'s and `status`'s refusals and of `check`'s cited archived experiment name the docs whose links to it count, not the docs further up a chain: designs, plans, investigations, reviews, experiments, then concepts, each in id order.
- Terminal conditions, which `archive` checks for the status it sets, `status` checks as for `concluded` when it sets an experiment `answered` or `concluded`, and `check` reports as errors on each archived doc, and as for `concluded` on each live answered or concluded experiment:
  - every doc: a non-empty `summary` and no template guidance, with the messages of [check](#check);
  - a plan archived as `done`: at least one slice, else `plan has no slices`, and each slice `done`: ``slice `<heading>` is <status>, not done``, or `is without status, not done`;
  - a review: `finding <id> is still open` for each finding whose disposition's first word is `open`;
  - a design: `known issue <id> is still listed; move it to the design that takes over, or remove it`;
  - an experiment: unless `Sources:` has a value or the status is `dropped`, ``Setup: `<label>` is empty (research lists `- Sources:` instead)`` for each of `Commit`, `Environment` and `Command` without one, and `Conclusion is empty` when that section holds only whitespace and template guidance;
  - an investigation: ``Reproduction: `<label>` is empty`` for `Commit`, `Environment` and `Command`, and ``Resolution: `<label>` is empty`` for `Root cause`, `Fix` and `Verification`.
- A label line is `Label: value` or `- Label: value`, `*` ignored so that `**Label:**` counts; indented lines below a label extend its value.

```text
canon.py archive ID STATUS
```

- `archive` changes no file and exits when the Git index has unmerged entries (`canon: resolve the merge conflicts first`), when an index start marker lacks its end marker ([D005§regeneration: regeneration](D005-docs-index.md#regeneration)), when no or several docs have ID, for D000 ([D002§project-overview-d000: D000](D002-overview-and-as-built.md#project-overview-d000)), when the doc is archived (`canon: <id> is already archived`) when STATUS is no terminal status of its type (`canon: <id> can be archived as adopted or dropped`, listing the type's), for an experiment archived as `concluded` whose status is another (`canon: <id> is <status>, not concluded; archive an experiment nothing absorbed as dropped`) or that a live doc cites (`canon: <id> is linked by <ids>; it stays live while a live doc cites it`), and for a design with a sub-design outside `archived/` (`canon: <id> has live sub-designs <ids>; archive them first`). A failed terminal condition prints `ERROR <path>: <problem>` for each and exits 1. `archive -h` lists each type's terminal statuses.
- Otherwise it sets `status` to STATUS and `updated` to today, from whatever status the doc has, and moves the doc to `<docs root>/archived/<type directory>/` under its file name and its attachment directory to `archived/<type directory>/<id>/`, with `git mv` in a Git checkout and a plain rename outside Git or when Git refuses. It regenerates the indexes ([D005§regeneration: regeneration](D005-docs-index.md#regeneration)), prints `<old path> -> <new path>` and exits 0.
- Every inline link or image, `[text](target)` outside code with a path as its target, in each `.md` file of the repository, every one Git tracks or would add or, outside Git, that the walk finds ([Layout](#layout)), that points at the moved doc or into its attachment directory follows the move, and the moved files' own links are rewritten for their new directory. A root-absolute link (`/path`) stays root-absolute, and a rewritten target percent-encodes whitespace, `%`, `#`, `?`, `(` and `)` in its path. `adopt` ([D004§adopt: adopt](D004-project-setup.md#adopt)), `rename`, `renumber` and `init`'s move of a design to D000 rewrite links by this rule too. A link whose anchor names a heading of a file the command rewrites, the moved doc, any doc whose citations the command rewrites ([D010§renumber: renumber](D010-doc-queries-and-renames.md#renumber), [D010§rename: rename](D010-doc-queries-and-renames.md#rename)) and any `.md` file whose link texts it changes, the file's own `#<anchor>` links included, gets that heading's anchor after the command, which differs when the command changes the heading, as `adopt`, `renumber`, `init`'s move and `rename` with `--title` change the H1, `renumber` the ids in headings and each of them the link texts and citations in headings, or shifts its numbered anchor (`<slug>-1`). The anchors settle: a heading that changes because a link or citation in it follows another heading's anchor gets its new anchor too, which the links and citations to it follow in turn. Headings pair in order, the H1 with the H1 and a heading the command rewrites with its rewritten text, and a heading the command adds, as `adopt` may prepend an H1 and `init`'s move appends D000's subsections, pairs with none; a link to a heading that pairs with none keeps its anchor. Link texts stay, except a reference's `§<anchor>`, which follows its anchor, the ids `renumber` changes and the title `rename` changes ([D010§rename: rename](D010-doc-queries-and-renames.md#rename)), and `adopt`'s labels. The docs whose links change keep their `updated`, so `check` reports each one HEAD holds until `check --fix`.

```text
canon.py status ID STATUS
```

- `status` moves a doc forward along its type's non-terminal statuses: design `draft`, `accepted`, `active`; plan `draft`, `accepted`, `in-progress`; experiment `planned`, `running`, `answered` and on to a live `concluded`; and concept `draft` to a live `adopted`. It may skip a status, as an as-built design goes from `draft` to `active`. Its one move back takes an `answered` experiment that no live doc cites to `running` for a later run ([Doc types](#doc-types)). A current status outside these counts as before all of them. `status -h` lists each type's statuses in order.
- It changes no file and exits 1 with `canon: <message>` at the first of these checks that fails, in this order, its lists comma-separated: when an index start marker lacks its end marker ([D005§regeneration: regeneration](D005-docs-index.md#regeneration)), when no or several docs have ID, when the doc is archived (`canon: <id> is archived`), when STATUS is not a status of the doc's type (`canon: <status> is not a status of <id>; use one of <the statuses it moves along for the type>`), when it is terminal, a concept's `adopted` and an experiment's `concluded` aside (``canon: <status> is terminal for <id>; use `canon.py archive` ``), when it does not come after the doc's status and is not that move back (`canon: <id> is <status>; status moves only forward`, followed by `, to <later statuses>` when there are any and, for an answered experiment, `, or back to running`), and when the move's condition fails (`canon: <id> needs <condition> to become <status>`, `<condition>` worded as here): `accepted` and `in-progress` need `reviewed` equal to `revision`, and a design's `active` needs `implemented` not above `reviewed`; a move that skips `accepted` needs its condition too, checked first. A missing or non-integer `reviewed` reads as 0, and the conditions hold only for a `reviewed` and an `implemented` of at least 1. An experiment's `answered` needs the terminal conditions of `concluded`. Its `concluded` needs the body of a live design or plan to link the experiment, checked first (`canon: <id> needs a live design or plan that links it to become concluded`), then those conditions. Its move back to `running` needs no live doc to cite it (`canon: <id> is linked by <ids>; a later run gets a new experiment that links it`). Each terminal condition that fails prints `ERROR <path>: <problem>`, as for `archive`, and `status` exits 1.
- Otherwise it sets `status` to STATUS and `updated` to today, regenerates the indexes ([D005§regeneration: regeneration](D005-docs-index.md#regeneration)), prints `<id>: <old status> -> <new status>` and exits 0. It sets no other field; [Frontmatter](#frontmatter) states who sets `reviewed`, `reviewers`, `approved` and `implemented`.

### Frontmatter

A doc starts with a `---` line, and its frontmatter ends at the next `---` line; without both, `check` errors with ``missing or unterminated `---` frontmatter`` and checks nothing else of the doc. Each non-blank line between is `key: value`, else ``unparseable frontmatter line: <line>``. A value loses surrounding whitespace and `'` or `"` characters. In a list field, `[a, b]` is a list, its items split at commas and stripped the same way, empty items dropped; in an integer field, digits alone make an integer.

```yaml
---
status: active
created: 2026-03-02
updated: 2026-05-17
revision: 4
modules: [auth, gateway]
summary: Token issuing, refresh and session lifecycle.
refs: [D001, D007]
owns: [auth-token, session]
paths: [src/auth/**, src/session/]
reviewed: 4
reviewers: [claude-opus-high, gpt-high]
implemented: 4
---
```

- Every type requires `status`, `created`, `updated`, `revision`, `modules`, `summary` and `refs`; designs also `owns` and `paths`, plans `based_on`. Designs may add `reviewed`, `reviewers`, `approved`, `implemented` and `as_built`, plans `reviewed`, `reviewers` and `approved`. `check` errors with ``missing frontmatter field `<key>` ``, ``unknown frontmatter field `<key>` `` for any other field, and ``` `<key>` must be a list like [a, b] ``` for a list field (`modules`, `refs`, `owns`, `paths`, `based_on`, `reviewers`) that is no list.
- `created`, `updated`: dates, ``` `<key>` must be YYYY-MM-DD ``` otherwise, and ``` `updated` is earlier than `created` ```. `updated` is the date of the doc's last content change ([check](#check)).
- `revision`: a positive integer (``` `revision` must be a positive integer ```) counting semantic changes: bumped when a goal, spec, plan, or a concept's Ideas or Open questions change meaning, never for wording.
- `modules`: the modules the doc concerns; empty means the whole project of its docs root.
- `summary`: one line, which feeds the index and `find`. Empty: ``` `summary` is empty ```, at the unfinished level ([check](#check)). Over 160 characters once trimmed: `WARN` ``` `summary` is <n> chars (max 160) ```.
- `refs`: ids of related docs, each an existing doc's (``` `refs` entry <id> does not exist ```), including every doc the body links to ([Links and references](#links-and-references)).
- `owns` (D): topics the design is the single authority for, kebab-case (``` `owns` entry `<topic>` must be kebab-case ```) and unique across non-archived designs of every docs root: `` topic `<topic>` is already owned by <id> `` on each later design.
- `paths` (D): globs, relative to the project directory, of the code the design governs; they drive `which`, `affected` and `audit`. Whitespace and leading `./` are ignored; `**/` matches any directories, none included, `**` anything, `*` any characters but `/`, `?` one character but `/`, and a trailing `/` everything below; an entry also matches every path below a match; other characters, `[` included, match themselves. `WARN` ``` `paths` entry `<entry>` matches no file ``` when no file of the project that `check` reads matches, except for an archived design and a design with no `implemented`, whose code may not exist yet. A revision of a design with `implemented` adds a file to `paths` once the file exists, in the docs step. D000's `paths` and docs, and why entries match whole files: [D002: Project overview and as-built designs](D002-overview-and-as-built.md).
- `reviewed`, `reviewers` (D, P): the revision that passed the review gate and who reviewed that revision, `manual:<model>` for a review the user ran, never accumulated across revisions; the gate sets them ([D007: Change tiers and the review gate](D007-change-tiers.md)). On a design or plan with `reviewed`: ``` `reviewed` must be an integer revision not above `revision` ``` and, with `reviewers` empty, ``` `reviewers` must list who reviewed revision <n> ```; another type gets only the unknown-field error. A plan `in-progress` without `reviewed`: ``plan in progress without `reviewed` ``. Otherwise, a design `accepted` or `active`, or a plan `accepted` or `in-progress`, whose `reviewed` differs from `revision`: ``revision <n> is not reviewed (reviewed: <r>); pass the review gate, then set `reviewed` and `reviewers` ``, `<r>` reading `none` without the field, a `WARN` that `--base` makes an error.
- `approved` (D, P): the latest revision the user approved ([D007§gate-status: gate status](D007-change-tiers.md#gate-status)), set on each target of an L2 gate whose approval request the user says yes to, by the session that asked; on each design a new plan's `based_on` names, to that revision, by `canon-plan` when the user starts it; and on a plan, to its revision, by `canon-implement` when the user starts it. A doc the user has not approved has none. On a design or plan: ``` `approved` must be an integer revision from 1 to `reviewed` ```, `reviewed` reading 0 without the field.
- `implemented` (D): the revision the code fully implements, required once the design is `active`; the docs step raises it once the code lands, and a revision that needs no code change raises it as [D007§gate-status: gate status](D007-change-tiers.md#gate-status) states. Below `revision`, the spec leads the code and the difference is an open plan's work, not a defect. Errors: ``` `implemented` must be an integer revision from 1 to `revision` ```; ``` `implemented` r<i> is above `reviewed` r<r>; implement only reviewed revisions ```; ``` `implemented` is set but status is `<status>`; a design whose code has landed is `active` ``` for `draft` and `accepted`; for an active design without it, ``active design needs `implemented`: the revision its code fully implements``, fixable with `implemented: 1` when the design's `revision` at HEAD, or in the work tree for a file HEAD lacks, is 1 and no non-archived plan names it in `based_on`.
- `as_built` (D): [D002§as-built-revisions: as-built](D002-overview-and-as-built.md#as-built-revisions).
- `based_on` (P): the design revisions the plan was written against, `D012@r4`; `new P --from` fills it. Errors: ``` `based_on` entry `<entry>` must look like D003@r4 ```, ``` `based_on` design <id> does not exist ```. While the plan's status is not terminal and the design's `revision` is above the entry's: `WARN` ``based on <entry> but <id> is at r<n>; re-check the plan and update `based_on` ``.

### Known issues, findings and slices

A design lists in `## Known issues`, present only while it lists any, the problems found in it or in the code it governs that are neither fixed nor declined:

```markdown
| ID | Severity | Issue | Source | Since | Next |
|----|----------|-------|--------|-------|------|
| D003-K1 | major | Refresh retries break D005§queue-limits | P007 gate | 2026-10-21 | decide |
```

- Ids run `<design id>-K1`, `-K2`, …, unique in the table. Severity is `blocker`, `major` or `minor`. Source is where it was found: a gate (`P007 gate`), a plan or one of its slices (`P007`, `P007 S3`), other work at the HEAD it ran on (`code review 3f9a1c2`, `docs step 3f9a1c2`, `L0 3f9a1c2`), an as-built revision of the commit it records (`as-built 3f9a1c2`), or a review finding (`R004-F2`). Since is the date it was recorded. Next is what it waits for: `decide` (the user's decision), `fix` (a code change), `L1` (a revision of this design) or `L2` (`/canon-design`).
- Rows are not spec: changing them bumps no `revision`, passes no gate and does not count as checking the design against its code. The change that resolves an issue deletes its row, or else the audit that finds it resolved; one the user declines leaves as [D007§design-problems: design problems](D007-change-tiers.md#design-problems) states. The section goes with its last row, and a design that lists any cannot be archived.
- How an agent reads the known issues of the designs it works from is [D007§design-problems: design problems](D007-change-tiers.md#design-problems)'s.

A review lists its findings in `## Findings`, one row each:

```markdown
| ID | Severity | Finding | Disposition |
|----|----------|---------|-------------|
| R003-F1 | major | Refresh races with logout | moved I012 |
```

Ids run `<review id>-F1`, `-F2`, …; Severity as above. Disposition is `open`, `fixed <commit>` or, for a fix made in a doc, `fixed <id>@r<revision>` (`fixed C001@r22`), `moved <id>` (handed to the C, D, P or I that now tracks it, a design as a known issue) or `declined <reason>`.

`check` reads as rows the lines of the section outside code fences that start with `|`, apart from a header row whose first cell reads `ID` in any case and separator rows of `-`, `:` and spaces; cells past the table's columns are ignored. It errors with:

- `known issue row must be | <id>-K<n> | severity | issue | source | since | next |`, or `finding row must be | <id>-F<n> | severity | finding | disposition |`, for a row whose first cell is not the doc's id, `-K` or `-F` and digits, or that has fewer cells than the columns;
- `duplicate known issue id <id>`, `duplicate finding id <id>`, and `<id> severity must be one of blocker, major, minor`;
- for a known issue: `<id> needs the issue and its source`, `<id> since must be the date it was recorded, YYYY-MM-DD`, `<id> since <date> is later than today` and `<id> next must be one of decide, fix, L1, L2`;
- for a finding: `<id> disposition must start with one of open, fixed, moved, declined`, ``<id> moved to unknown doc `<id>` `` when no doc has the id after `moved`, and ``<id> fixed in unknown doc `<id>` `` when what follows `fixed` has the form `<id>@r<n>` and no doc has the id; otherwise what follows `fixed` or `declined` goes unchecked.

A `## Known issues` section with no row, well-formed or not, gives `WARN` ``` `## Known issues` lists no issue; delete the section ```.

A plan's slices are the `### ` headings of `## Slices` outside code fences. A slice's status is the first `Status:` line, optionally after `- ` and with `*` ignored, before the next slice; `check` errors with ``slice `<heading>` needs a `Status:` line with one of todo, in-progress, done, paused`` when it is missing or another value. The `S1: <name>` form and the `Risk:` line go unchecked.

### Links and references

- A section is referenced as `[D003§token-refresh: refresh flow](../designs/D003-auth.md#token-refresh)` and a whole doc as `[D003: auth design](../designs/D003-auth.md)`, never by line number. Each standard lives only in the design that owns its topic, and everywhere else links to it.
- `check` reads the inline links `[text](target)` and images `![alt](target)`, with an optional `"title"`, outside fenced code and inline code, in each numbered doc below its frontmatter, each project's `AGENTS.md`, the `.md` files under `guides/` and `assets/`, the `.md` files in attachment directories, live and archived, and an index file while it is up to date ([D005§check: check](D005-docs-index.md#check)). It skips a target with a URL scheme or starting with `//`, resolves `/path` from the repo root and any other path from the file's directory, percent-decoded, and errors, with the line, as `ERROR <path>:<line>: <message>`:
  - `broken link <target>` when nothing exists there;
  - `missing anchor #<anchor>` for an anchor in the same file, `missing anchor #<anchor> in <path>` for a `.md` target, that no heading's slug matches;
  - for a link, not an image, to a numbered doc: `link to <id> must read [<id>: ...] or [<id>§slug: ...] with #slug` unless the text starts with the doc's id, an optional `§<section>`, `: ` and a non-space character, and `link text section and #anchor differ; use [<id>: ...] or [<id>§slug: ...] with #slug` when the section and the anchor differ, a missing one counting as empty.
- A heading's slug is its text with links reduced to their text and backticks dropped, trimmed, lowercased, every character other than letters, digits, `_`, `-` and spaces dropped and spaces turned into `-`; a second heading with the same slug gets `-1`, a third `-2`. Headings in fenced code do not count, and trailing `#` characters of a heading are no part of its text.
- Each numbered doc a doc links to, other than through an image or to itself, belongs in its `refs`, links in its attachments aside: ``linked docs missing from `refs`: <ids>``, fixable by appending them in sorted order.

### check

```text
canon.py check [ID|PATH ...] [--fix] [--base REF] [--staged | --rev REV]
```

- `check` checks one tree: by default the work tree, the files [Layout](#layout) names; with `--staged`, the stage-0 entries of the Git index, the file `GIT_INDEX_FILE` names when it is set, other than intent-to-add entries (`git add -N`), which no commit records, so that in a pre-commit hook it checks what the commit records, under `git commit <paths>` and `git commit -a` too; with `--rev REV`, the tree of commit REV. In it, `check` checks every doc of every docs root, archived ones included, with the rules of this design, D000's and `as_built`'s ([D002: Project overview and as-built designs](D002-overview-and-as-built.md)) and the index's ([D005§check: check](D005-docs-index.md#check)).
- Under `--staged` and `--rev`, each of those rules that reads a file, its text, or whether a file or directory exists reads the tree checked through Git commands that change nothing, such as `git ls-files -s`, `git ls-tree -r` and `git cat-file --batch`, never the work tree: a file exists when the tree holds it, a directory when the tree holds a file below it, a symbolic link counts as what its target is in the tree, the target read from the link's blob as a path relative to the link's directory and followed through at most 40 links, and is no file when that target leaves the tree or is missing, and a submodule is no file. The version check of [D004§project-version: project version](D004-project-setup.md#project-version) reads the work tree's `AGENTS.md` and adds its `WARN` in every form of `check`.
- With ID or PATH arguments, `check` checks the work tree but reports only the problems on the named docs' files and on the `.md` files in their attachment directories, reading the rest of the repository as context: other docs, `AGENTS.md`, guides, the indexes and deleted docs go unchecked. A problem between two docs, such as a duplicate id or owned topic, counts as on each of them. An argument of the id form ([Ids and file names](#ids-and-file-names)) names the doc with that id, resolved as `archive` resolves its ID; any other names the doc whose file it is, relative to the working directory, else `check` ends with `canon: <arg> names no doc; give a doc id or the path of a doc file`. The summary line counts the named docs.
- Before reading any doc, `check` ends with the first of these that applies:
  - `canon: --staged and --rev check different trees; give one of them` when both are given;
  - `canon: --fix edits the work tree, which --staged and --rev do not check; drop one of them` for `--fix` with either;
  - `canon: check with doc arguments checks only those docs in the work tree; drop --base, --staged and --rev` for ID or PATH arguments with any of them;
  - `canon: --staged and --rev read Git; run check in a Git checkout` for either outside Git;
  - ``canon: unknown ref <REV>; fetch it first or correct the name`` when REV names no commit or starts with `-`;
  - ``canon: <REV> is a shallow commit, whose parents this clone lacks; fetch them with `git fetch --deepen=1` `` under `--rev` when the file `git rev-parse --git-path shallow` names lists REV;
  - `canon: resolve the merge conflicts first` under `--staged` when the Git index has unmerged entries.
- It prints one line per problem, sorted by path and then line, `<LEVEL> <path>[:<line>]: <message>` with `ERROR` or `WARN`, then `canon check: <docs> docs, <errors> errors, <warnings> warnings`, followed, on the work tree without `--fix`, by `; <n> fixable with --fix` when any problem is. It exits 1 when there is an error, else 0.
- This design's `WARN` problems are a long `summary`, the line limits, `paths` entries that match no file, a Known issues section without issues, a plan behind its `based_on`, a revision pending review, an unlinked adopted concept, an uncited concluded experiment and a cited archived experiment. The unfinished level applies to an empty `summary` and to template guidance: `WARN` for a doc whose status is one of its type's non-terminal statuses, other than a design `accepted` or `active`, a plan `accepted` or `in-progress` and an experiment `answered`, and `ERROR` otherwise, a live adopted concept and a live concluded experiment included. Under `--base`, every unfinished-level problem and every pending review is an `ERROR`; `--staged` and `--rev` leave both as on the work tree. Its other problems are errors.
- Unlinked adopted concept: `adopted, but no design links it` for an `adopted` concept outside `archived/` that the body of no design, live or archived, links.
- Uncited concluded experiment: `concluded, but no live doc cites it; link it or archive it as concluded` for a `concluded` experiment outside `archived/` that no live doc cites ([Statuses and archiving](#statuses-and-archiving)).
- Cited archived experiment: `concluded, but linked by <ids>; a cited concluded experiment stays live, so move it and its attachment directory out of archived/ and fix the links, or remove the links that do not rest on its result` for an experiment archived as `concluded` that a live doc cites ([Statuses and archiving](#statuses-and-archiving)).
- Template guidance: ``template guidance `<!-- canon: ... -->` left in the doc`` when a line outside fenced code, inline code removed, holds `<!-- canon:`.
- Line limits: a file's lines are counted as `wc -l` counts them, plus a last line without a newline. `WARN` `<n> lines (max 500)` for a numbered doc outside `archived/` over 500, followed for a top-level design by `; split into sub-designs (<id>A, <id>B, ...)`, for a sub-design by `; make it a new top-level design`, for a concept by `; split it into several concepts`, and for any other doc by `; move detail into <path>/`, `<path>` being its attachment directory relative to the repo root; `WARN` `<n> lines (max 150); move detail into docs` for a project's `AGENTS.md` over 150.
- `updated`: in a Git checkout, for a doc whose file in the tree checked differs from its version under the same path in the commit compared, when the lines other than those starting with `implemented:` or `as_built:` differ, and `updated` equals that version's and is not the day of the check: ``content changed but `updated` was not bumped``, fixable on the work tree with today's date. The commit compared is HEAD, when there is one, for the work tree and `--staged`, and under `--rev` REV's parent when REV has exactly one; a root or merge commit gets no `updated` check. The day of the check is today, and under `--rev` either REV's author date or its committer date, each in the time zone the commit records (`git log -1 --format=%ad%n%cd --date=short REV`).
- `--fix`, without doc arguments, first exits on an index start marker without its end marker ([D005§regeneration: regeneration](D005-docs-index.md#regeneration)). It runs the checks and applies each fix, setting the field, in place or as a new line before the closing `---`, or deleting it, and prints `fixed <path>: set <field>` or `fixed <path>: deleted <field>` for each; it regenerates the indexes as D005 states, then checks again and prints that result. The fixes are `refs`, `updated`, `implemented`, `as_built` and the indexes. With doc arguments, `--fix` applies only the fixes of the problems it reports.
- `--base REF` makes the unfinished level and pending reviews errors and adds the deleted-doc and collision checks against the branch ([Ids and file names](#ids-and-file-names)), whose tip is HEAD, or REV under `--rev`. Before any fix, `check` ends with the first of the `--base` errors that applies, `<tip>` reading `HEAD` or REV:
  - `canon: no merge base with <REF>` without a HEAD commit, outside Git included, unless `--rev` is given;
  - ``canon: unknown ref <REF>; fetch it first or correct the name`` when REF names no commit or starts with `-`;
  - ``canon: no merge base with <REF> in this shallow clone; fetch the full history with `git fetch --unshallow` `` when REF shares no history with the tip and the checkout is shallow (`git rev-parse --is-shallow-repository` prints `true`), as CI checkouts often are;
  - `canon: no merge base with <REF>` when REF shares no history with the tip;
  - `canon: cannot diff against <REF>...<tip>: <reason>`, with Git's reason, when Git cannot diff against REF otherwise.
- `check`, `new` and `archive` end with `canon: git <subcommand> failed in <dir>: <reason>` when Git fails to list the files, read a file of the tree checked, look HEAD or REV's parents and dates up, diff the tree checked against the commit compared or list unmerged entries, rather than read the failure as an empty result.

### Concurrent work

The agent-facing text of this section is the `canon` skill's Rules.

- Top-level sessions that work in one repository at the same time each work in a linked worktree on a branch of their own, at `.worktrees/<branch>` in the repo root, made with `git worktree add --track -b <branch> .worktrees/<branch> <base>` run at the repo root of the checkout the session starts in, `<base>` being the branch checked out there, so that `<branch>@{upstream}` names the branch the change comes from. A session that will edit files takes one before its first edit when the user says that another session works, or will work, in its checkout, unless the host already started it in a linked worktree of its own. Before that first edit, a top-level session not yet in a worktree of its own that finds in `git status --porcelain` changes that neither the user nor a handoff it resumes told it about asks the user whether another session works in the checkout, and takes a worktree if one does. When `git check-ignore -q .worktrees/<branch>` finds the path not ignored, as in a project whose `init` predates the `.gitignore` line ([D004§init: init](D004-project-setup.md#init)), the session first adds the line `.worktrees/` to the `info/exclude` file of the directory `git rev-parse --git-common-dir` prints, which changes no tracked file.
- Every session in a checkout shares its uncommitted changes, its Git index and its `.canon/`, so one session's `check --fix`, `git add -A`, `git checkout -- <path>`, stash or review snapshot acts on another's work too. A session told only after it has edited that another works in its checkout stops editing, lists the files it changed and asks the user whether another session edits any of them; once the user settles that, it finishes the change in place, commits only its own changes as below, and takes a worktree for its next change.
- A worktree runs its own install of canon ([D004§install: install](D004-project-setup.md#install)): in a project that commits only `skills-lock.json`, the session first runs `npx skills experimental_install` at the worktree's root. Its `.canon/` and review snapshots are its own ([D003§review-snapshots: review snapshots](D003-subagents.md#review-snapshots)), and its trace data goes where [D001§switch-and-storage: switch and storage](D001-skill-telemetry.md#switch-and-storage) says, the main checkout's trace directory when the session can write there.
- The change stays in its worktree until it is done: a session that hands it on, with a next-phase command or a handoff, names the worktree's path, since a new session starts in the checkout its host opens. Before the branch goes back, the session updates it from its upstream with a merge or rebase in the worktree, runs `check --fix` there, settles with `renumber` each id both branches took ([Ids and file names](#ids-and-file-names)) and commits, so the branch merges back with no `check --fix` in a checkout another session uses. Merging it back, `git worktree remove .worktrees/<branch>` and deleting the branch are the user's to do, or a session's that the user asks.
- A subagent takes no worktree: it works in the checkout of the session that launched it. A session working in a linked worktree starts every subagent prompt, in every round, with the worktree's root as the directory to work in, and runs a reviewer's command from that root, since a host starts subagents in the workspace the session opened, the checkout it started in.
- In one checkout, one session at a time stages and commits, since the Git index is shared; canon's `archive`, `rename`, `renumber` and `adopt` stage too, moving files with `git mv`. A subagent that edits docs, such as a worker or a researcher writing an experiment, checks and fixes only those with `check <ids> [--fix]` ([check](#check)), which leaves the other docs and the indexes alone; the session that commits checks the rest.
- A session commits part of a checkout's changes, such as its own beside another session's or one change of several, in four steps:
  1. When the commit holds numbered docs, run `check --fix <ids>` on them.
  2. Check that `git diff --cached --name-status` lists nothing but its own changes, else ask the user. Stage the files by path with `git add <path>`. Of a file that also holds changes it does not commit, stage only its own hunks, applying a patch of them with `git apply --cached`; when it cannot tell its hunks from the others, ask the user.
  3. Run `index --staged`, which stages the index lines of the staged docs ([D005§regeneration: regeneration](D005-docs-index.md#regeneration)), then `check --staged`.
  4. Commit with `git commit` and no paths: `git commit <paths>` and `git commit -a` commit the whole work-tree content of the files they take, others' changes in them included.

### Writing rules

Agents and people read docs, usually after reaching them through a pointer: an `AGENTS.md` line, a link, a `find` hit on a summary or heading. `writing.md` applies to every doc:

- Say each thing once, in the doc that owns it, and link to it everywhere else. A design other than D000 states what it owns, and what it leaves out only where a reader would likely assume otherwise; it never states what other designs own.
- Name a doc that does not exist yet by its topic, never by a guessed id: `new` assigns ids.
- Use the fewest plain words that state the exact meaning; a reader new to the project understands the doc without the conversation that produced it.
- Record only the final state: no discussion history, superseded drafts or "X rather than Y" contrasts with an earlier proposal. A rejected alternative stays only as a one-line Decision when it is likely to be proposed again.
- State the correct approach. A counter-example is added only for a typical, likely misuse, and a prohibition only as a hard guardrail, paired with the behavior to follow instead.
- Prefer numbers to adjectives, code (signatures, schemas, commands) to prose for interfaces, and lists to tables unless the facts are short and tabular.
- Keep a diagram's source with it: Mermaid in the doc, or the generating script in the attachments beside the image it renders, with how to install its dependencies. Its labels stay text a reviewer can read, never outlines or a raster image, and it changes in the commit that changes what it shows.
- Write `summary` lines, titles and headings as pointers that lead with the words a reader would search for.
- Keep a topic's definition, rules and caveats under one heading.
- Order the sections a doc type leaves free, such as a design's Spec subsections, and the content within each from the whole to the parts and the core to the details, so a reader meets the frame before what fills it. Among those sections, define each term or name before the first one that uses it; where that cannot be, or another doc defines it, link the definition at its first use.
- Record what the repository cannot tell (reasons, unwritten conventions, gotchas), and name the command or file for facts the environment already states.
- Cut every sentence that changes nothing a capable reader would do anyway.
- `AGENTS.md` holds only the pointers and rules every session needs; detail goes into designs.
- Design for the project's real constraints: a feature's input validation, the permissions its spec states and protection of the data it handles are part of the feature. Further security hardening comes only when the project or feature is security-related or the user asks, and the design states it.
- Avoid wording that rots, such as "currently", "new" or "recently"; the frontmatter carries time.
- Write docs in the project's documentation language, keeping the template's section headings, labels and table headers in English, since `canon.py` parses them.

## Decisions

- A doc is archived, never deleted, and its id is never reused: the id is a doc's identity (the `canon` skill's Rules).
- A link to a doc carries the doc's id in its text, and for a section the section's slug (the `canon` skill's Rules; reason unknown, kept as found).
- Frontmatter is a flat subset of YAML, one `key: value` per line with `[a, b]` lists, that `canon.py` parses itself, since it runs on the standard library alone ([D000§decisions: decisions](D000-project-overview.md#decisions)).
- Brackets make a list only in list fields, so a `summary` such as `[a, b]` stays text (0b2c737; `test_brackets_make_lists_only_in_list_fields`).
- A change to the `implemented` or `as_built` line alone needs no `updated` bump: `implemented` tracks the code and `as_built` the pending gate, not the doc (`content_lines` in `canon.py`; `test_setting_implemented_alone_needs_no_updated_bump`).
- `check --fix` gives `implemented: 1` only to an active design never revised and named by no open plan: a design becomes active once its code lands, so one never revised implements r1, while for a revised design only the code and the history can tell (`check_doc` in `canon.py`; `ImplementedTest`; 6fc017c).
- An empty `summary` and template guidance only warn until a design or plan passes its gate, a concept is adopted, an experiment is answered or a doc is archived, and fail under `--base` (0b2c737; reason unknown, kept as found). `--staged` and `--rev` keep them, and pending reviews, at their work-tree level, since a commit may hold a draft before its gate (the user's decision, 2026-11-12).
- Code review and the review gate produce no R doc; what the user leaves for later becomes a known issue of a design or a line in a plan's Notes ([D007§merging-findings: merging findings](D007-change-tiers.md#merging-findings)) (1c7c1f0; reason unknown, kept as found).
- `archive`, `adopt`, `rename`, `renumber` and `init`'s move of a design to D000 share one link rewriting, so all encode targets alike, and the design that takes on the moving commands owns its rule: D006, with `archive` (the user's decision).
- The line limit warns and never fails, on every type (`check_doc` in `canon.py`; reason unknown, kept as found), and its hint names how each type grows out, since sessions cut content they had just added to fit a concept under it (R003-F29).
- An adopted concept stays live and the design wins where they differ: mirroring each design revision into the concept made it an ungated second spec (R003-F19; the user's decision, 2026-11-11).
- A concluded experiment stays live, like an adopted concept, and leaves `experiments/` only once no live doc cites it or its result is replaced or found wrong: archiving each experiment once absorbed hid the evidence live docs rest on from `find` and readers who skip `archived/`, and experiments a project archived as `concluded` stay valid ([R003§r003-f17-archived-experiments-hide-live-evidence: R003-F17](../archived/reviews/R003-silk-design-phase.md#r003-f17-archived-experiments-hide-live-evidence); the user's decision, 2026-11-11). Concepts, reviews, investigations and later experiments rest on that evidence as designs and plans do, so a link from any of them keeps it live; `superseded`, `overturned` and `dropped` archive it whatever links it, since a replaced, wrong or moot result is no evidence to keep in view. Superseding moves only the links of designs and plans, which state what the project relies on; other docs keep theirs, and the predecessor's `refs` name its successor (the user's decision, 2026-11-13).
- A link from a concluded experiment counts only while that experiment is cited itself, so concluded experiments that link one another do not keep each other live once nothing else cites them (the user's decision, 2026-11-13).
- `check` reports a live doc's link to an experiment archived as `concluded`, but only warns, as for an uncited live one: a project that archived each experiment once absorbed, before concluded experiments stayed live, can hold many such links, and only a hand move out of `archived/` settles one whose links rest on its result (the user's request, 2026-11-13).
- `concluded` needs a live design or plan that links the experiment, so the status means absorbed, not only answered; a link from another doc keeps a concluded experiment live but concludes none (the user's decision, 2026-11-11).
- An experiment with a written Conclusion that nothing has absorbed is `answered`, so `running` always means a run or research under way and readers see which answers wait for a design; it is named `answered`, since `finished` reads as a synonym of `concluded` (the user's decision, 2026-11-11).
- A later run extends an answered experiment that no live doc cites, but never a cited one, which it would change under the docs that cite it; the experiment it fully replaces is archived as `superseded` (the user's decision, 2026-11-11).
- An experiment whose question no longer matters, run or not, is archived as `dropped`, and only a concluded one as `concluded`, so an archived `concluded` still means answered and absorbed (the user's decision, 2026-11-12).
- Canon maintains docs only in the project's documentation language and has no translation convention: translations kept beside the docs doubled every edit and still drifted, and readers can translate with their own tools, such as an editor or browser extension ([R003§r003-f27-translations: R003-F27](../archived/reviews/R003-silk-design-phase.md#r003-f27-translations); the user's decision, 2026-11-13).
- Sub-designs have one level: a sub-design that outgrows itself becomes a new top-level design (`doc-types.md`; reason unknown, kept as found).
- Markdown in attachment directories gets the link checks of guides: reports and other Markdown live there, and sessions wrote their own link checkers for them ([R003§r003-f33-links-in-attachments: R003-F33](../archived/reviews/R003-silk-design-phase.md#r003-f33-links-in-attachments)).
- A design with no `implemented` gets no warning for `paths` that match no file, as a planned module's Path gets none ([D002§project-overview-d000: project overview](D002-overview-and-as-built.md#project-overview-d000)): in a project still being designed, the same warnings for code not yet written buried new ones at every `check` ([R003§r003-f32-permanent-warnings: R003-F32](../archived/reviews/R003-silk-design-phase.md#r003-f32-permanent-warnings); the user's decision, 2026-11-11).
- `status` moves non-terminal statuses forward and checks each move's condition, leaving every other field to the steps that set it: `draft`, `accepted` and `active` were hand edits sessions got wrong ([R003§r003-f36-no-status-command: R003-F36](../archived/reviews/R003-silk-design-phase.md#r003-f36-no-status-command); the user's decision, 2026-11-11).
- `new` refuses a plan without `--from` rather than warn after creating it: a plan comes only from an accepted or active design, and one created without it takes an id for good and lacks `based_on` and the link to its design (the user's decision, 2026-11-13).
- Sessions that work at the same time take a linked worktree and branch each: sharing one checkout, a project's sessions rewrote each other's docs with `check --fix`, committed each other's work with `git add -A docs`, reverted it with `git checkout` and overwrote a doc under review ([R003§r003-f14-sessions-sharing-one-checkout: R003-F14](../archived/reviews/R003-silk-design-phase.md#r003-f14-sessions-sharing-one-checkout)), and in this repository `git commit -- <path>` took another session's uncommitted edit of the same file into 2b6309b. The worktrees sit inside the repository, since agent sandboxes allow writes only inside the workspace, under a dot directory, which walkers that skip hidden directories, such as Go's `./...` and pytest's collection, leave alone ([C001: Canon backlog](../concepts/C001-canon-backlog.md); the user's decision, 2026-11-12).
- A session takes its worktree before its first edit, and one told of another session only after editing finishes that change in place: moving uncommitted changes to a new worktree would mean reverting them in the shared checkout, where `git checkout -- <path>` also drops another session's changes in the same files (2026-11-13). It stops and asks the user which of its files another session edits, since it cannot know the other's files and finishing in place there would overwrite another's work (gate of D006 r17).
- A worktree's branch tracks the branch it was made from: Git keeps that in the repository's config, where every later session finds the branch to update from and merge back into, while a handoff records only the current branch (follow-up of D006 r17).
- Besides the user's word, uncommitted changes nobody told a top-level session about make it ask before its first edit: a session cannot see another, and in this repository another session's uncommitted change first made `validate.py` fail and then entered 2b6309b. The question costs one answer when the changes are the user's own (the user's decision, 2026-11-13).
- The session updates its branch and runs `check --fix` and `renumber` in the worktree before the branch goes back, and merging and removing the worktree are the user's: run in the main checkout, `check --fix` and `renumber` would rewrite the docs of a session still working there, and when a branch merges is the user's call (gate of D006 r17).
- A session adds `.worktrees/` to `info/exclude` when the project does not yet ignore it, rather than to `.gitignore`: the edit would be an uncommitted change in a checkout another session uses, while `init` adds the `.gitignore` line on its next run (gate of D006 r17).
- Subagents take no worktree, and a session in a worktree names its root in every subagent prompt: a host starts subagents in the workspace the session opened, the checkout it started in, whose files are another branch's; workers run one at a time and reviewers only read, so the session's worktree serves them all, and the session stays the one that stages and commits there (2026-11-13; gate of D006 r17).
- `check` with doc arguments, `check --staged` and `index --staged` serve what worktrees do not: a subagent allowed to edit only its own docs, and a session splitting a checkout's changes into several commits. Sessions skipped `--fix` and hand-built index blobs at each commit (R003-F14, R003-F39; the user's decision, 2026-11-12).
- `check --staged` and `--rev` read the tree through Git rather than a checkout of it: sessions built temporary worktrees or used `git archive` to check a commit ([R003§r003-f34-checking-a-commit-or-the-staged-state: R003-F34](../archived/reviews/R003-silk-design-phase.md#r003-f34-checking-a-commit-or-the-staged-state)), and in a pre-commit hook only Git's index view shows what `git commit <paths>` or `git commit -a` records, since Git then points `GIT_INDEX_FILE` at another index (the user's decision, 2026-11-12). A symbolic link counts as its target in the tree, as the work tree's `check` follows links, so a project whose `AGENTS.md` or linked file is a link passes or fails alike in the hook (gate of D006 r17). The staged tree leaves out intent-to-add entries: Git lists one as a stage-0 entry holding the empty blob, as it lists a staged empty file, yet `git commit` records none, so reading it would fail the hook on a file the commit does not hold and list it in the index `index --staged` stages (the user's decision, 2026-11-13). Such an entry is told from a staged empty file, which the commit holds and `check` checks, by `git diff --cached`, which leaves intent-to-add entries out, never by its content (follow-up of D006 r17).
- `--rev` checks `updated` and deleted docs only on a commit with one parent: a root commit has no earlier version, and a merge has one per parent, each side's changes checked by its own commits and by `--base`. REV's author and committer dates both count as the day of the check, since a commit checked later was made on its own date and a rebase or amend gives it a later committer date (the user's decision, 2026-11-12).
