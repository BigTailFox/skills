# D004: Project setup

## Goals

1. One idempotent command, `canon.py init`, sets a repository or a monorepo module up for canon, and the same command upgrades the project to the running `canon.py`. A project holds no copy of `canon.py`: it runs from the `canon` skill installed in the project, pinned to a release, and the project records only the canon version it was last set up with.
2. `canon.py adopt` turns an existing markdown file into a canon doc, keeping its Git history and every inline link to it.
3. The `canon-init` skill takes the user through setting a project up, upgrading it and adding a module.

Out of scope: what `init` does with D000, and the D000 and as-built steps of setup and upgrade ([D002§project-overview-d000: D000](D002-overview-and-as-built.md#project-overview-d000), [D002§setup: setup](D002-overview-and-as-built.md#setup)); the reviewer file `canon-init` writes ([D003§reviewers: reviewers](D003-subagents.md#reviewers)); tracing, which `init` never turns on ([D001§switch-and-storage: switch](D001-skill-telemetry.md#switch-and-storage)).

## Spec

Every canon skill runs the `scripts/canon.py` of the `canon` skill it follows, so that the text an agent follows and the `canon.py` it runs come from one install; the `canon` skill's Tool section states this for agents, and `canon.py` below means that file. A subagent given only a prompt, such as a reviewer, runs the one the Tool line of `AGENTS.md` names. The paths in the output are relative to the repo root, the top of the Git work tree or, outside Git, the directory the command runs in; `--root` and FILE are relative to the directory the command runs in.

### Install

- canon is installed in each project, pinned to a release: at the repo root, `npx skills add BigTailFox/skills@<tag> -s '*' -a claude-code -a codex -a cursor -y`. `<tag>` is the newest release, the name after `refs/tags/` on the first line of `git ls-remote --tags --refs --sort=-v:refname https://github.com/BigTailFox/skills 'v*'`; releases are tagged `vX.Y.Z`, with no pre-release suffix. The command puts the skills in `.agents/skills/`, which Codex and Cursor read, links each from `.claude/skills/` for Claude Code, and records the tag in `skills-lock.json`. It names the agents because `npx skills` run inside one agent targets only that agent and those reading `.agents/skills/`, and for Claude Code alone copies into `.claude/skills/` instead ([E001§npx-skills-181-project-install: npx skills](../experiments/E001-skill-scope-precedence.md#npx-skills-181-project-install)). When `skills-lock.json` lists `canon`, `npx skills experimental_install` installs the release it records instead ([E001§pinning-and-restoring-with-npx-skills-181: pinning](../experiments/E001-skill-scope-precedence.md#pinning-and-restoring-with-npx-skills-181)).
- canon recommends committing the installed skills with the project, `.agents/skills/` and the agents' links to it, as `npx skills` intends a project install to be shared, so that every clone, worktree and CI job runs the release the project pins with nothing to install. The user may commit only `skills-lock.json` instead and restore the skills with `npx skills experimental_install`, in CI too; `canon.py` works the same either way.
- An installed skill file is the repo root's `skills-lock.json`, the repo root's `.agents/skills` or a file under it, or a symbolic link in the repository whose target in the work tree is that directory or lies under it, such as `.claude/skills/canon`. The target is compared with `.agents/skills` unresolved, so when `.agents/skills` is itself a link, the files it points to keep their own kind, and a path that is no link in the work tree, such as one only an earlier commit holds, counts by its path alone. canon treats it as tooling, neither code nor doc ([D002§installed-skills: installed skills](D002-overview-and-as-built.md#installed-skills)). The copies a `--copy` install puts in an agent's directory are not installed skill files.
- `canon.py` runs only from inside the project. Every command but `-h` and `--version` first checks, running no Git command, that the absolute path it was started by lies under the nearest directory at or above the working directory that holds `.git`, a directory or a file; outside Git, under the working directory or a directory above it that holds an `AGENTS.md`. A path lies under a directory when one of the directories it passes through is that directory, compared as the same directory, so a symbolic link above the checkout, such as macOS's `/tmp`, does not refuse it. Links on the path itself stay unresolved, so that tests and scratch repositories run the working tree's `canon.py` through a link at their own `.agents/skills/canon/scripts/canon.py`. A linked worktree thus runs its own install, not the main checkout's. Otherwise the command changes no file and exits with ``canon: canon runs only from an install inside the project, and this canon.py is <path>; install canon in the project as https://github.com/BigTailFox/skills#install says, and remove a user install of canon with `npx skills remove -g` ``. This check comes before the version check.
- An agent that finds the canon block in `AGENTS.md` but no `canon` skill, or whose `canon.py` refuses to run from outside the project, as in a first `/canon-init` from a user install, tells the user that canon manages the project, or is about to, and asks whether to install it in the project. On a yes it installs as above, and when the user also has canon installed for every project, asks whether to remove that install with `npx skills remove -g` and the canon skills' names, since Claude Code would keep running it and Cursor and Codex would offer both ([E001: Precedence of project and user skills across hosts](../experiments/E001-skill-scope-precedence.md)). An agent whose `canon.py` refuses to run as older than the project ([Project version](#project-version)) asks the same about installing a newer release. After an install, the agent reads the skills it follows again from the project's install.

### Project version

- The project's version is the `CANON_VERSION` of the `canon.py` that last ran `init` at the repo root. The canon block of the repo root's `AGENTS.md` records it in its Tool line as `canon version <n> or later` ([init](#init)). A block without that phrase, written while projects kept a copy, records no version.
- Every command but `-h` and `--version`, when the repo root's `AGENTS.md` has a canon block, a start marker with an end marker after it, first compares the running `CANON_VERSION` with the version the block's first line starting `- Tool:` records:
  - Below it: the command changes no file and exits with ``canon: this project needs canon version <n> or later, and this canon.py is version <m>; install a newer canon release as the canon block of AGENTS.md says``.
  - Above it, or with no recorded version: the command carries on after printing to standard error ``canon: this project is set up for canon version <n>; run `/canon-init` to upgrade it to version <m>``, or with no recorded version ``canon: this project records no canon version; run `/canon-init` to upgrade it to version <m>``. `check` reports the same message, without `canon: `, as a `WARN` line on `AGENTS.md` instead, counted among its warnings, and `init` at the repo root prints nothing, since it records the running version.
  - Equal: nothing.
- The version check runs no Git command, as the location check does: it reads the `AGENTS.md` in the directory holding `.git` that the location check found, or outside Git in the working directory.

### init

```text
canon.py init [--root DIR] [--hook]
```

- The project is the repo root, or the module directory `--root` names. A `--root` that is not an existing directory inside the repository makes `init` change no file and exit with `canon: --root <dir> is not a directory inside the repository`. A run with nothing to change prints `canon init: nothing to do`; otherwise `init` prints one line per change, such as `created <path>`, `updated <path>` and `wrote <index>`.
- With unmerged entries in the Git index, `init` exits with `canon: resolve the merge conflicts first` before changing any file.
- **Old copy.** In a Git checkout, a tracked file named `canon.py` that holds a `CANON_VERSION = "<n>"` line is a copy kept from when projects held one, unless it is an installed skill file or the `scripts/canon.py` of a directory whose `SKILL.md` has `name: canon`, such as the canon source in this repository. `init` at the repo root leaves it and prints, before its change lines, ``warning: the project no longer keeps a copy of canon.py; remove <path> and replace `python3 <path>` where files still name it, such as CI and each `docs/README.md` ``, and `check` reports the same message, without `warning: `, as a `WARN` line on the file while it is tracked.
- **Repository files.** `.gitattributes` gets each missing line of `**/docs/README.md merge=union` and `**/docs/archived/README.md merge=union`, and `.gitignore` gets `.canon/` and `.worktrees/`, the linked worktrees of sessions that work at the same time ([D006§concurrent-work: concurrent work](D006-doc-model.md#concurrent-work)), each unless a line already names it, `.canon` or `.worktrees` with or without slashes. Both are at the repo root and are created when missing.
- **`AGENTS.md`.** A run without `--root` writes the canon block into the repo root's `AGENTS.md`: the `## Docs` section of the template in `canon.py`, between a start and an end marker, the HTML comments `canon:agents:start` and `canon:agents:end`. The section tells an agent without the `canon` skill to ask the user whether to install it, with the commands of [Install](#install) in full, since such an agent has no canon skill to read them from; it names D000 and the index ([D002§project-overview-d000: D000](D002-overview-and-as-built.md#project-overview-d000)), its Tool line reads ``- Tool: `scripts/canon.py` of the `canon` skill installed in this project, `.agents/skills/canon/scripts/canon.py` as `npx skills` installs it, canon version <n> or later, run from the repo root (`-h` lists commands). …``, where `<n>` is the running `CANON_VERSION` ([Project version](#project-version)), and that line ends by having `check --fix` run before committing and after every merge or rebase, except in a checkout another session also uses or for a commit of only part of a checkout's changes, which follow the `canon` skill's Concurrent work ([D006§concurrent-work: concurrent work](D006-doc-model.md#concurrent-work)); its tier line asks for each change's tier before starting, unless the change touches only docs that no design's `paths` names and bumps no revision ([D007§change-tiers: change tiers](D007-change-tiers.md#change-tiers)). Without `AGENTS.md`, `init` creates one holding `# AGENTS.md` and the block. Without a start marker, it appends the block; otherwise it replaces the text from the first start marker to the first end marker after it. A start marker in the repo root's `AGENTS.md` with no end marker after it makes every run, a module's included, change no file and exit with ``canon: the repo root's AGENTS.md has a canon block start marker with no end marker after it; fix the markers and rerun `init` ``.
- A module run leaves the repo root's `AGENTS.md` alone. A module without an `AGENTS.md` gets one holding `# AGENTS.md` and a line that links the module's `docs/README.md` and says the repo root's `AGENTS.md` defines the docs rules; a module's existing `AGENTS.md` stays as it is.
- **Docs index.** When the project's `docs/README.md` is missing, `init` creates it with an intro that names `canon.py find <words>` and an `## Index` heading. Each run then regenerates every index ([D005§regeneration: regeneration](D005-docs-index.md#regeneration)).
- **D000.** At the repo root only, as [D002§project-overview-d000: D000](D002-overview-and-as-built.md#project-overview-d000) states.
- **`--hook`.** In a Git checkout, `init` writes the pre-commit hook at the path `git rev-parse --git-path hooks/pre-commit` prints, with mode 755 and lines ending in `\n` on every platform. The hook runs `check --staged`, which checks what the commit records ([D006§check: check](D006-doc-model.md#check)), with the `canon.py` of `.agents/skills/canon/scripts/`, where `npx skills` installs it, relative to the work tree's top, where Git runs hooks. Where that `canon.py` predates `--staged`, as on a branch or worktree whose install is older, the hook runs `check`. It holds, `<V>` being the first `CANON_VERSION` whose `check` takes `--staged`:

  ```sh
  #!/bin/sh
  c=.agents/skills/canon/scripts/canon.py
  if [ ! -f "$c" ]; then
    echo "canon: no canon skill installed in this checkout; install it as the canon block of AGENTS.md says" >&2
    exit 1
  fi
  v=$(python3 "$c" --version) || exit 1
  [ "${v#canon }" -ge <V> ] 2>/dev/null && exec python3 "$c" check --staged
  exec python3 "$c" check
  ```

  An existing hook stays, one `init` cannot read included. One that holds exactly the hook above is current, and `init --hook` prints nothing for it; for any other, `init --hook` prints ``kept the existing pre-commit hook; add `canon.py check --staged` to it``. The exceptions are the hooks earlier versions wrote: one holding exactly the lines `#!/bin/sh`, `c=.agents/skills/canon/scripts/canon.py`, `[ -f "$c" ] && exec python3 "$c" check`, then the hook's `echo` line unindented and `exit 1`, each ending with a newline, as versions 48 to 57 wrote it, and one holding exactly `#!/bin/sh`, a newline and `exec python3 <path> check`, with any path free of whitespace and an optional final newline, as a project with a copy had. Every `init` at the repo root, with or without `--hook`, replaces either with the hook above, setting mode 755, and prints `updated <hook path>`. Outside Git, `--hook` does nothing.
- When `init` cannot write or replace the hook, such as where `.git` is read-only, it still finishes every other step and prints ``warning: cannot write the pre-commit hook: <reason>; rerun `canon.py init --hook` where .git is writable``.

### adopt

```text
canon.py adopt FILE TYPE [--slug SLUG] [--title TITLE] [--root DIR]
```

- TYPE is a letter of C, D, P, R, E and I in either case, or a type's directory name, plural or singular, such as `designs` or `design`.
- The project is `--root`, a project directory or its `docs/`, else the nearest directory above FILE that holds an `AGENTS.md` other than an installed skill file, up to the repo root. The doc gets the next free id of its type, which history keeps taken as [D002§project-overview-d000: D000](D002-overview-and-as-built.md#project-overview-d000) states, allocated under the lock `.canon/id.lock`, and moves to `<project>/docs/<type directory>/<id>-<slug>.md`. SLUG defaults to the kebab form of FILE's name without `.md` ([D006§ids-and-file-names: ids and file names](D006-doc-model.md#ids-and-file-names)).
- Links to FILE, or into it with an anchor, follow the move, and FILE's own links are rewritten for its new directory, by the rule of [D006§statuses-and-archiving: statuses and archiving](D006-doc-model.md#statuses-and-archiving), except that a link to FILE, not an image, whose text is not a reference gets the text `<id>: <text>`, or `<id>§<anchor>: <text>` when it has an anchor, the text defaulting to the id when empty.
- FILE's frontmatter is dropped, printing `dropped frontmatter fields: <names>`, and replaced with a new doc's frontmatter for the type: its first status, `created` and `updated` today, `revision: 1`, empty `modules`, `summary` and `refs`, and empty `owns` and `paths` for a design or `based_on` for a plan. FILE's first H1 becomes `# <id>: <title>`, where TITLE defaults to that H1's text, else to the slug with each `-` replaced by a space and the first letter capitalized; without an H1, that line is prepended. Each section the type requires that FILE lacks is appended as `## <name>` with a guidance comment asking for the matching adopted content.
- In a Git checkout the move is a `git mv`, so history follows the file; outside Git, or when Git refuses the move, as for an untracked FILE, it is a plain rename. `adopt` then regenerates the indexes ([D005§regeneration: regeneration](D005-docs-index.md#regeneration)) and prints `<old path> -> <new path>`.
- `adopt` exits without changing a file when nothing exists at FILE (`canon: <file> does not exist`), FILE is not a `.md` file (`canon: <file> is not a markdown file`) or is already a canon doc (`canon: <file> is already a canon doc`), when SLUG is not kebab-case (with the message `new` gives, [D006§templates-and-new: templates and new](D006-doc-model.md#templates-and-new)), TYPE is unknown (`canon: unknown type <type>; use one of C D P R E I`) or the project has no `AGENTS.md` (``canon: no AGENTS.md at <absolute path>; set the project up with `canon.py init` first``), when the Git index has unmerged entries, and when another command holds the id lock for 60 s.

### The canon-init skill

- The skill runs the flow the user names. Otherwise it runs Setup when the repo root's `AGENTS.md` has no canon block. In a project set up, it runs, in this order, Upgrade when the project's version is below the running `CANON_VERSION` or not recorded ([Project version](#project-version)), then the reviewer setup when [D003§reviewers: reviewers](D003-subagents.md#reviewers) says to run it alone; when neither holds, it asks the user which flow to run. A Setup or Upgrade that stopped before its end resumes only when the user names it.
- **Setup**, in order:
  1. Survey the existing docs, skipping generated and vendored files and leaving docs by their name and each docs root's `README.md` in place ([D002§setup: setup](D002-overview-and-as-built.md#setup)). In a monorepo, find the modules that get a docs root: independently built or released packages and services.
  2. Propose one line per file, naming its type, `guides/`, the doc it folds into or that it stays in place, and the modules that get a docs root, and whether to commit the installed skills, as canon recommends, or only `skills-lock.json` ([Install](#install)); wait for the user's approval.
  3. Run `init` at the repo root, then `init --root <module>` for each module.
  4. `adopt` each mapped file and move guides into `docs/guides/` with `git mv`. Commit before restructuring, so Git still pairs the renames, with the installed skills, or with `skills-lock.json` alone and the installed skills' paths in `.gitignore`, as step 2 settled.
  5. Restructure: move content into the required sections, state each standard only in the design that owns it, fill `summary`, `modules`, `owns` and `paths`, fold each ADR into its design as a Decision line, removing the ADR, fold docs about the whole project into D000 as [D002§setup: setup](D002-overview-and-as-built.md#setup) states, and archive docs about finished or obsolete work.
  6. Write D000 as [D002§setup: setup](D002-overview-and-as-built.md#setup) states.
  7. In `AGENTS.md`, leave the canon block as `init` wrote it, move spec-like content from the rest into designs and remove instructions that conflict with canon, such as old doc conventions. A project that uses Claude Code gets the line `@AGENTS.md` in its `CLAUDE.md`, created when missing, unless `CLAUDE.md` already imports it or is the same file as `AGENTS.md`, and loses the instructions there that conflict with canon too.
  8. Set up the reviewer file ([D003§reviewers: reviewers](D003-subagents.md#reviewers)).
  9. In a project with CI, add a job that runs `python3 .agents/skills/canon/scripts/canon.py check --base origin/<default branch>`, with a fetch depth that reaches the merge base, after `npx skills experimental_install` in a project that commits only `skills-lock.json`.
  10. Pass D000 and the adopted designs that describe existing code through their gates ([D002§setup: setup](D002-overview-and-as-built.md#setup)).
  11. Run `check --fix` until it reports no error, and commit as `docs: adopt canon` with a `Refs:` trailer naming D000 and those designs.
  12. When the user wants a pre-commit hook, run `canon.py init --hook`, and give the user its warning's command when it cannot write the hook.
- **Upgrade**: a project that kept a copy has no install of canon yet: install it as [Install](#install) says, and ask whether to commit the installed skills or only `skills-lock.json`, committing them with the upgrade as Setup step 4 does. Otherwise, when a newer release than the one `skills-lock.json` records for `canon` exists, offer to install it, and on a yes install it and run the new `canon.py` from here on. From the repo root, run `canon.py init`. When it warns that the project no longer keeps a copy, ask the user whether to remove the copy, then replace `python3 <copy>` where files name it: in CI with the job of Setup step 9, elsewhere, such as each `docs/README.md`, with `canon.py`. Then run `check --fix`, and fix what the new version still reports apart from D000's guidance. `--fix` gives `implemented: 1` only to an active design never revised and without an open plan; every other active design gets the revision its code fully implements, found by comparing the code with each revision of its spec in the Git history, or the open plan's `based_on`. A plan in progress whose `reviewed` is below its `revision` passes the review gate before its slices continue. When `init` moved the design owning `architecture` to D000, commit its output as it is before anything else, so Git keeps the rename, with `--no-verify` when a pre-commit hook runs `check`, since the guidance `init` appended fails `check` until the D000 work replaces it. A project that had no D000 then continues as [D002§setup: setup](D002-overview-and-as-built.md#setup) states.
- **Add a module**: run `canon.py init --root <module>`, then add or update the module's row in D000's Modules table, linking the designs in the module's docs root.
- `canon-sync`'s audit starts by looking for a newer release than the one `skills-lock.json` records for `canon`, found as [Install](#install) finds the newest, and offers to install it and run Upgrade.

## Decisions

- Projects hold no copy of `canon.py` and run that of the `canon` skill installed in the project, since canon must not write files of its own into the user's assets beyond the docs system (the user's decision; R003-F31). A copy lagged the installed skills, whose text then contradicted its errors (D004-K1, R001-F2).
- canon recommends committing the installed skills, as `npx skills` intends a project install, so that clones, worktrees and CI run the pinned release with nothing to install and the pin lives in one place, where a CI job installing a tag of its own would be a second pin to keep in step (the user's decision). The skills are the user's commit under that tool's convention, not files canon writes.
- An installed skill file is known by its path under `.agents/skills/`, where `npx skills` always puts a project install, while the agents' directories it links from number in dozens and include a plain `skills/` at the repo root, which the project's own code may use. A `--copy` install, which skips `.agents/skills/`, is rare enough to leave to D002's advice of narrower module Paths (the user's decision).
- canon is installed in each project, pinned to a release, an agent installs or updates it only after asking the user, and `canon.py` refuses to run from outside the project (the user's decision). Each project then runs the version it pins, and projects canon does not manage load none of its skills. Where a user install exists beside the project's, Claude Code runs the user's and Cursor and Codex load both and leave the choice to the model ([E001: Precedence of project and user skills across hosts](../experiments/E001-skill-scope-precedence.md)), so the refusal turns a silently bypassed pin into an error. It catches a user install's text too because each skill runs the `canon.py` of the install whose text it follows: run from the project's install instead, the user's text would follow its own version unchecked (D004 r5 gate).
- The location check finds the project as D001 finds the checkout's root, without Git: `trace` runs no Git command while tracing is off, and the check holds where Git is missing or refuses the checkout. A linked worktree therefore runs its own install rather than the main checkout's, which committed skills give every checkout (D004 r5 gate).
- An old copy is any tracked `canon.py` with a `CANON_VERSION` line outside a canon skill, and `check` warns on it while it is tracked: once `init` has rewritten the canon block, the block no longer names the copy, so a warning tied to the block would show once and an Upgrade stopped after `init` would leave CI running the copy unnoticed (D004 r5 gate).
- A `canon.py` older than the project's version refuses to run, and a newer one only reminds (the user's decision). An older one would report a newer version's docs as errors that contradict the project, as a version 18 copy reported `as_built` as unknown; refusing names the cause. Updating the skills then never blocks work in a project not yet upgraded.
- The canon block keeps the template's words, also in a project documented in another language, since `init` rewrites it on every run at the repo root (the user's decision).
- The pre-commit hook runs `check --staged`, and every `init` at the repo root replaces the hook earlier versions wrote to run `check` on the work tree: Git points the hook's `GIT_INDEX_FILE` at what the commit records, `git commit <paths>` and `git commit -a` included, so the hook checks the commit and not another session's uncommitted work, and it fails on a stale index, which only warns on the work tree ([D005§check: check](D005-docs-index.md#check); the user's decision, 2026-11-12). It falls back to `check` by version because Git runs one hook for every worktree and branch of a repository while each checkout runs its own install, and an older `canon.py` rejects `--staged`, which would block every commit there (gate of D006 r17).
- `init` adds `.worktrees/` to `.gitignore` in every project: unignored, a linked worktree there shows in the main checkout as an untracked directory that `git add -A` records as an embedded repository (the user's decision, 2026-11-12).
- Setup installs the pre-commit hook last: the hook's `check` fails on every file step 5 has yet to restructure, so it would reject step 4's commit, which comes first to keep Git's rename pairing (R001-F14).
- Upgrade commits `init`'s move of the design owning `architecture` on its own, with `--no-verify` under a hook running `check`, so Git keeps the rename (the user's decision; f767510, P002's Log).
- `adopt` replaces FILE's frontmatter instead of merging it, printing the fields it dropped (`adopt_doc` in `canon.py`; reason unknown, kept as found).
