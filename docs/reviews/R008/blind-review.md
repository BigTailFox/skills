# Independence and procedure in Canon blind review

This assessment follows the nine sections and two subsections of `canon-blind-review` at `0311d34`, with Canon CLI 86. The exact skill text is available with `git show 0311d34:skills/execution/canon-blind-review/SKILL.md`. [Skill](../../../skills/execution/canon-blind-review/SKILL.md)

## What belongs in the short entry point

1. Start each first-round reviewer in a fresh context. Give it only a self-contained brief with the target, requested delivery, reading scope and assessment criteria. It reads the repository itself. Keep the author conversation, rationale offered in chat, expected verdict and other reviewers' findings out of that brief. A fresh reviewer using the author's model can do this. The calling workflow or user specifies any additional independent roles.
2. Give each reader a stable, read-only target. Hold the worktree at the reviewed version while readers are active. First-round reviewers stay out of `.canon/` and form their own verdicts independently of the other reports. Later prompts may give access to the specific snapshot diff needed for a confirmation or follow-up.
3. Credit an assessment to the reviewer and version it actually covered. Keep the complete original report and its available source evidence. Count a delivered pass once. A missing required pass stays pending unless the user grants an exception allowed by the calling workflow. A waiver discharges the named obligation and gives nobody reviewer credit.

The first two rules govern what can influence a verdict. The third lets the maintainer verify whose verdict was delivered about which change. Canon's prompt currently instructs reviewers to respect the reading and writing limits. Enforcing the actual context, permissions and accessible files requires the host or launcher. For an ordinary second opinion, lead from the target to a neutral prompt, a fresh reviewer and its report. An interrupted dispatch points to recovery. An unavailable route points to manual fallback. A fix for an accepted major or blocker points to confirmation. ## Review evidence and reviewer configuration

- `review-evidence.md` serves two readers. Put round inputs, report coverage, confirmations and handoffs with `canon-blind-review`. Keep the shared record format and its validation in the CLI. Optional tracing can reuse the verified record and explain its own archive and replay. Coverage checks and review snapshots still serve the review when tracing is off. [D007§checking-required-review-coverage: review coverage](../../archived/designs/D007-change-tiers.md#checking-required-review-coverage) · [D003§review-snapshots: snapshots](../../archived/designs/D003-subagents.md#review-snapshots)
- `reviewer-example.md` can live with `canon-blind-review`, which consumes the machine-local configuration. Point to that skill from `canon-init` when configuring a reviewer. A review reads the filled configuration.

| Prompt | Keep the neutral brief in the entry point. Put the report language, finding format, known-issue rule and minor-finding limit in the template for the reviewer. | The CLI could render the template from the caller's targets, criteria and baseline. | Reviewers | At dispatch, use the roles specified by the caller. For a cross-family command, apply the user's grant before transmitting inputs. | Launch | Start fresh first-round contexts with the target held stable. Current policy launches reviewers together. Keep parallel launch as the fast default. A host could run them sequentially on the same version if each sees only its own brief. Read host and missing-notification details when they apply. | `review start` can pin inputs. The orchestrator still holds the live checkout steady. The host creates the fresh context and provides the real job handle. |
| External review progress | Read when running an external reviewer. It covers permission display, output streaming, heartbeats and querying the original job. | A CLI could store observed job and session bindings. The launcher or host observes activity, displays output and handles permissions. |
| Review files | Keep the verbatim terminal report, actual source and reviewed version together. Consult the file layout when handling evidence manually or recovering it. | `review start` prepares gate, code-review and follow-up rounds. A standalone second opinion still needs a fresh directory, `snapshot` and a manually saved baseline. Extend preparation to that case and let the CLI allocate keys and store the evidence. Version 86 already checks run IDs and can distinguish identical reports on a target using distinct run IDs or verified manual returns. |
| Stopped runs | Read on timeout, silence or publication failure. Check the original job first. Recover its completed report or wait on it if still running. Partial output earns no credit. User cancellation ends the run. | Once the host supplies the actual job state, the CLI could track retries, recovery limits and artifact destinations. The host or provider determines whether the same session can resume. |
| Manual fallback | Read when an eligible route is unavailable or the configuration selects manual review. Give the user the same neutral prompt and verify the returned model, target and snapshot. Only the user can waive a missing cross-family pass for named L2 design or plan revisions. L2 code review awaits the report. | The CLI could render the manual prompt and save a receipt from the actual return message or attachment. Version 86 already checks the supplied evidence and scoped exceptions. |
| Merge | After independent reports arrive, preserve their sources and assess each finding against scope and evidence. Agreement on an in-scope finding favors acceptance. Expanding the task goes to the user. | The CLI could link source findings and record a disposition supplied by the orchestrator. Deciding that two findings make the same claim, or that a suggested fix is justified, takes judgment. |
| Confirmation | Read after accepted blockers or majors have been fixed. One scheduled round gives the original reviewer its claim, fix location and scoped diff. Credit the actual confirmer if an allowed delegate takes over. Open or new blockers go to the user before another fix or recheck. | `snapshot` captures the fixed tree. The CLI could prepare the diff from that reviewer's own input and render the prompt. The reviewer decides whether the fix resolves the claim. |
| Targeted recheck | Read when the user requests a separate recheck. Revisit the named claim and preserve the first verdict alongside the later result. | For a recorded unit, `trace blocker` and `trace recheck` can append evidence after closure. The CLI could prepare the named claim and its diff before dispatch. |
| Follow-up round | Read when a gate reviews a later revision. Keep its tier and criteria. Returning reviewers can assess changes to targets they covered in full. A finding confirmation covers its claim alone. Added targets need the missing full passes. A previously waived role needs a fresh independent read or a new scoped waiver. | `review start --kind follow-up` and `review check` already handle round inputs and declared coverage. The CLI could generate scoped diffs and prompts from the last verified baseline for each reviewer and path. |
