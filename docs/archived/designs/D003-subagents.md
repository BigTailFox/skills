# D003: Subagents

## Goals

1. Every subagent a canon skill launches starts with nothing from the session that launches it, so a review stays blind, every slice starts in an empty context window, and subagents meant to differ, such as alternative interface designs, do not inherit the session's assumptions.
2. Reviewers and workers run on the model and reasoning effort the user set for the session; only the cross-family reviewer names its own model.
3. A subagent that the workflow continues is resumed whenever the host allows it, so it keeps its context: a reviewer judges the fixes against its own findings, a blocked worker continues with the answer, and a run that stopped finishes instead of starting over.
4. The cross-family reviewer is set up once per user and machine, outside every checkout, so the tools and logins it needs never enter a repository and every clone and linked worktree finds it.

## Spec

This design covers the subagents of the `canon` workflow, meaning the reviewers of the review gate, of code review and of any other blind review and the workers of `canon-implement`, the review snapshots their confirmations diff, and the setup of the cross-family reviewer. Subagents that other skills launch for their own steps, such as a codebase review's angles, research, broad searches or alternative interface designs, follow those skills, except that each is a new subagent ([Launch](#launch)). What a review assesses, and how its findings are merged, belong to the review gate and code review.

### Launch

- Every subagent a canon skill launches is a new subagent from the host's own tool: the Task tool in Cursor, the Agent tool in Claude Code, multi-agent subagents in Codex. None is a fork of the session. This covers same-model reviewers, workers and a cross-family reviewer that runs as a host subagent, which can instead run as a command ([Reviewers](#reviewers)), and the subagents other skills launch for their own steps. Each skill says so where it launches one: the `canon` workflow, `canon-blind-review` and `canon-implement` for reviewers and workers, `canon-review` for its angles, `canon-research` for its researcher, `canon-grill` for its searches, and `canon-codebase-design`'s Design It Twice for its alternative designs.
- Reviewers and workers are launched without a model or effort, so they run on the session's, which the user sets. Only a cross-family reviewer that runs as a host subagent gets a model, the one the reviewer file names. Since every worker runs at the session's effort, `canon-plan` names a plan's slices that carry a `Risk:` line beside its closing command and suggests high reasoning effort for the implementation session.
- In Claude Code a reviewer is a `general-purpose` or custom subagent, since the built-in Explore and Plan agents cannot be resumed. A worker is a general-purpose subagent.
- A gate launches its first-round reviewers in parallel, and code review issues its reviewers together. On a host that can await command and host reviewers together, launch them in a parallel foreground batch. Otherwise start the command on a retained job and launch the host reviewers asynchronously. Before yielding with a reviewer outstanding, check its original job or bound host run for a terminal report. Recover completed output from that run and continue waiting on a running one. The command keeps its output attached to the progress surface selected under [External review progress](#external-review-progress). A lone host reviewer may run in the foreground. While a review's reviewers read, in any round, the session edits nothing in the work tree outside `.canon/`, so each reads what the review snapshot records; it fixes findings once the reports are in. When a required report is unavailable and all active readers have stopped, the pending-gate procedure in [D007§unavailable-cross-family-review: unavailable review](D007-change-tiers.md#unavailable-cross-family-review) governs work on the reports received. Workers run one at a time, in plan order; work without a plan has no worker.
- A session working in a linked worktree launches its subagents there, a reviewer's command included, as [D006§concurrent-work: concurrent work](../../designs/D006-doc-model.md#concurrent-work) says.
- The launching session keeps each reviewer's and worker's id: a reviewer's agent ID, or the running command's session binding and the published report's ID, in its review files ([D001§review-files: review files](../../designs/D001-skill-telemetry.md#review-files)), and a worker's agent id in `.canon/canon-implement/<P id>/S<n>-id.txt`.

### Input and reports

- The `canon-blind-review` skill states what every blind review shares: the prompt's rules on reading and writing, its report contract and known-issue rule, launching, the review files and snapshots, stopped runs of reviewers, the manual fallback, the merge baseline, and the confirmation and follow-up rounds with their prompts. The review gate in the `canon` workflow and `canon-code-review` state only what is their own, such as the gate's Target, As-built and Assess lines, merge rules and status, and code review's briefs; `canon-review`'s angle reviewers report as that contract says. The workflow names these skills without a fallback for when one is missing, since the skills are installed together ([D000§goals: goals](../../designs/D000-project-overview.md#goals)).
- A reviewer's only input is its prompt, which names files in the repository for it to read. For a code review the prompt names the requested delivery from the plan or task, quoting or paraphrasing only its requirements. If the scope is unavailable, the reviewer reports that uncertainty and checks the contracts the diff touches. Every first-round prompt is the `canon-blind-review` template, whose Target lines, Assess items and reading line, a whole sentence, the caller fills: the review gate with the lines of its reviewer prompt in the `canon` workflow, a code review with the diff command, the untracked files, the commit list and its sources. It never gets the conversation, a summary of it, or the author's reasoning, worries or expected verdict. On every route the prompt is what forbids it to modify any file, write scratch files or read `.canon/`, and what allows it the project's `canon.py` with `show`, `find`, `which`, `affected` and `check` without `--fix`, which read only, or the files themselves when the host blocks such a call. Every prompt asks for the report in the project's documentation language, which takes precedence over the user's language for the session. A confirmation or follow-up prompt allows in `.canon/` only its diff command, which reads the review snapshots ([Review snapshots](#review-snapshots)); a confirmation prompt needs no `canon.py`, since it names where each fix is.
- The session saves each report of a reviewer that runs as a host subagent, first-round or confirmation, verbatim in that run's findings file, `<key>.md` or `<key>-confirm.md`, never a translation or summary, and merges it in whatever language it came. A run's report is saved once that file is newer than the run's prompt file, which the session writes before launching the run; a notice for a saved report changes nothing, since hosts can repeat a notice or deliver it late. Once the session has no other work, it looks for the report of a run whose notice has not come in the host's record of the run, where [D001§sources: sources](../../designs/D001-skill-telemetry.md#sources) names one. A reviewer that runs as a command writes its findings file itself, and the session reads it when the command ends.
- A reviewer of a gate or blind review reports every blocker and major finding and at most 10 minor ones, each with its severity and location, then its Questions, and ends with one line, `Verdict: approve` or `Verdict: revise`. A code review reviewer reports findings with severity `blocker`, `major` or `minor`.
- A confirming reviewer answers resolved or not resolved for each finding listed, citing the location that shows it, assigns each new blocker the fixes introduce a stable report-local B1, B2, … label, and ends with a Verdict line. The gate or code review records these answers as [D001§review-dispositions: review dispositions](../../designs/D001-skill-telemetry.md#review-dispositions) describes.
- A worker's only input is the worker prompt, filled with the plan's path, its slice and the design sections the slice builds on, and followed, for a replacement, by the answer its predecessor was blocked on; the plan carries the rest. The prompt has it build the slice test-first, keep its scratch files in `.canon/canon-implement/<P id>/S<n>/`, edit no plan or design and not commit, and tells it that it cannot reach the user and that search tools which honor `.gitignore` skip `.canon/`.
- A worker stops and reports `blocked` when the plan or a design cannot be followed, naming which and the fix it would propose, or when a decision is needed that the docs and code do not settle; it reports `stuck` when a failing test stays unexplained and its last two attempts produced no new evidence narrowing the cause; otherwise it reports `done`. The report gives the status, the files changed, the tests added with their seams, the test commands run and their results, deviations from the plan and open questions.
- On `done`, the session re-runs the slice's tests and checks that the diff stays within the slice and edits no plan or design.

### Reviewers

- **Same-model reviewer**: a subagent on the session's model and effort. Every gate has one, and code review has two, its Spec and Standards reviewers, each launched the same way.
- **Cross-family reviewer**. Use the first eligible reviewer of a different family in the initiating family's order. After its stopped runs exhaust recovery, try the next eligible reviewer. Launch additional reviewers when the user requests them. Give each reviewer whose report is used its own [D001§review-files: review key and files](../../designs/D001-skill-telemetry.md#review-files). A replacement that produced no report earns no credit. It runs for an L2 code review, for another blind review when the user requests a second family, and at the gates specified by [D007§review-gate: review gate](D007-change-tiers.md#review-gate).
- **Reviewer file**. A single machine-local `$XDG_CONFIG_HOME/canon/reviewer.md` (default `~/.config/canon/reviewer.md`) serves all checkouts. Put `Reviewer priorities` first. An explicit family order takes precedence, followed for an unlisted family by the named default order, then the legacy unheaded list. Ordered Markdown references identify named definitions, with host-specific entries and `none` for a family or a particular host. An explicit applicable `none` ends selection. Skip the initiating family and entries the host cannot run. Under `Reviewer definitions`, give each stable name one definition with its family, model, effort, supported hosts, prerequisites and launch route. To share a command, give it one named Markdown heading and link to it from each definition, supplying the model and effort there. A host subagent specifies its host and model. A command opens a fresh read-only session. Substitute the round’s prompt-file path for `<prompt>` and its findings-file path for `<out>`. Declare its destination, inputs, allowed tools, how to identify the session and observe or resume the job. Apply [Authorization for command reviewers](#authorization-for-command-reviewers). Keep provider settings and credentials on the machine. Existing inline per-family definitions and unheaded fallback entries retain their ordering, host restrictions and fallback meaning. Normalize the configured families when setup next edits them.
- **Migration and writes**: a session that needs the reviewer file and finds none copies there an earlier setup's `.canon/canon-blind-review/reviewer.md` from the current checkout or the main one, and reads its route definitions in place when the copy fails. Import only route definitions and priorities. Discard any claim of a grant from checkout-controlled content, including a file read in place. A user-approved file copy authorizes the copy alone. The file lies outside the workspace, so a sandboxed session writes it with the user's approval; when a setup's write fails, the review takes the manual route.
- **Setup**. The workflow's Subagents section and `canon-init` use this same file. When the family has neither a runnable reviewer nor an applicable `none`, collect its order and verify each route with a small read-only prompt using the tool's help. Inspect the published output and early session identity. Query the trial job with its declared status command and, when resume is offered, demonstrate a read-only continuation of that test session using its observed ID. Record `none` when the user declines or has no reviewer, scoped to the current host when other hosts keep their entries. Record only capabilities the route demonstrated. Preserve unrelated families, hosts and shared definitions on a targeted setup. A review configures only its family. A user-requested setup covers the families they name. Apply the grant rules below before sending even a read-only trial or continuation.
- **Manual fallback**. After every eligible first-round route is exhausted, or when setup cannot write the file or an applicable `none` is configured, report the reason and offer the filled prompt for an independent manual review. `canon-init` can change a configured `none`. Save a returned report with its prompt, credit `manual:<model>` and leave the session ID empty. A gate awaiting this report follows [D007§unavailable-cross-family-review: unavailable cross-family review](D007-change-tiers.md#unavailable-cross-family-review).

### Authorization for command reviewers

Both setup entry points use the example in the core `canon` skill, `reviewer-example.md`, linked from its workflow. Record a real grant in the machine reviewer's route definition after the user explicitly accepts the displayed scope. A current conversation grant also applies within its stated scope. Its record names:

- The authorizing user decision and its source, the provider destination and model, and the allowed read-only tools.
- The repositories, by canonical absolute Git common directory (shared by linked worktrees), or canonical project root outside Git. Other clones need explicitly listed identities. Route preferences remain available in every checkout.
- Permitted inputs, such as the review prompt, named docs, source, tests and diffs, with any narrower path limits; and the authorized phases: setup trial, design, plan, code review, confirmation or recovery as granted.
- Lifetime: the named batch or a standing grant with the user's chosen expiry or until revoked. Revocation in the conversation or removal or revocation of the saved grant stops further use. A sample, a repository file, a migrated copy or a model's assertion cannot establish consent. Imported claims need an independent user decision before use.

Apply the same match before setup trials, first runs, follow-ups, confirmations, replacement or recovery. Pass only the permitted prompt and inputs, using a route that restricts what can reach the provider to the granted scope. For example, a documentation-only grant can use explicitly selected files or an isolated view containing them; read-only access to an unrestricted checkout does not enforce a narrower file grant. If the route cannot apply the limit, obtain an appropriate grant or use the existing manual path. Choose an already authorized eligible replacement when present. Otherwise ask for the preferred eligible route if it is needed. One matching grant covers its specified calls without a repeat consent question from the agent. Cite its source and scope in the host's actual permission request. The host decides permission for the operation. This authorization concerns transmission of review inputs.

### External review progress

Prefer the host's native view of the launched command. In Codex App, the desktop host, run the command once with its flushed stdout/stderr attached to its native command item. An integrated terminal is usable when the host can attach that same job. Use the equivalent native command surface on other hosts that expose one. Launch through the ordinary host permission mechanism. Include the destination, inputs and matching grant in its request metadata; if the host cannot show that context there, give one notice before submitting the request. Grant approval and confirmed process start are distinct.

On a streaming route the launcher emits the events it observes: process start, first and subsequent reviewer activity, elapsed time, optional idle heartbeats and exit status. Restrict the result returned to the agent to completion or an actionable failure and the report location. Routine events go directly to the command view. Wait for completion or use the original job’s wait handle without periodic progress queries or chat messages. A supported launcher persists the provider ID and binding locally as the opening event arrives, including while the caller is waiting; select a recoverable route only when this behavior was demonstrated. A route lacking an observable ID or activity advertises only its actual capabilities.

For a buffered host or an unattached job, give one notice that live output is unavailable and wait quietly on that job. Use its read-only status operation for a requested update, interruption or recovery decision. Show required decisions, failure or the final outcome in chat. Use chat for routine progress only at the user's request.

Bind the absolute checkout, round, report path, provider, model and session ID together in per-attempt state keyed by output. Retain the binding across a caller deadline. Publish the merged run's ID to its report-stem ID file, leaving it empty for an ID-less result. Preserve earlier reports and their ID files. Only a complete terminal report enters findings.

After a wait times out, check the original job. If it is still running, continue waiting on that job. A deadline that actually terminated a run permits resuming the same provider session, prompt, read-only scope and output after fresh tool or model activity. A recovering launcher can also finish publishing an already completed report. Allow at most two deadline recoveries per attempt, fewer if the route sets a lower limit. A terminated attempt with no new reviewer activity since its preceding launch or recovery, an exhausted recovery limit, or a terminal provider failure is one stopped attempt. Heartbeats and polling supply no activity. The first stop allows one retry under [Stopped runs](#resuming-and-replacing). A second stop exhausts that reviewer. A route without a usable session or recovery mechanism follows that same retry limit. User cancellation ends the run. Keep provider-specific commands, inactivity deadlines, status transports and credentials in the local configuration.

### Resuming and replacing

- **Stopped runs**: a subagent whose run stops before it reports, because the host reports it interrupted, timed out or failed, or its record shows the run ended without a report, gets one more run, as does a reviewer command that exits without publishing a complete terminal report to `<out>`. It is resumed by its id, given only a request to continue where it stopped and end with the report its prompt asks for; when it cannot be resumed, a new one given the same prompt replaces it and starts the work over. For an interrupted command use [External review progress](#external-review-progress). A terminally failed or non-resumable command gets one retry before moving down the configured order. When that run stops or fails too, the session stops trying: a worker's slice pauses, with the stopped runs as its problem; a first-round cross-family review moves to the next eligible, authorized reviewer who has no active or completed pass for these targets in this round, taking the manual route when none remains or the user required that specific reviewer; findings the cross-family reviewer cannot confirm, and its part of a follow-up round, go to the resumed same-model reviewer, as under Confirmation and Follow-up; and a same-model review waits for the user.
- **Confirmation**: after accepted blocker or major findings are fixed, the reviewers that raised them confirm the fixes in one round, given only the confirmation prompt of the `canon-blind-review` skill and what this list adds to it. Before the first round, and again once the fixes are made, the session takes a [review snapshot](#review-snapshots), keeping the first one's id in `snapshot.txt` and the second's in `snapshot-confirm.txt` among the review's files. The confirmation prompt's diff command, `git -C .canon/canon/snapshots diff <first> <second> -- <paths>` with the paths of the files the fixes touched, shows only what the fixes changed, untracked files included, whether or not anything was committed, and the prompt allows that command and nothing else in `.canon/`. A late or supplemental reviewer uses its own recorded input snapshot and fixed snapshot under [D007§target-coverage: target coverage](D007-change-tiers.md#target-coverage). The session runs the command first: when a snapshot failed, the first id is lost or the command fails, the prompt says that no diff is available, and the reviewer reads the fixes at the locations it lists. A reviewer that runs as a host subagent, same-model or cross-family, either code review axis included, is resumed by its id: the Task tool's `resume` in Cursor, SendMessage to the agent id in Claude Code, and `send_input` to the agent id in Codex, after `resume_agent` when the agent was closed. Each confirmation prompt includes only the findings assigned to that reviewer for confirmation. For each it quotes the original finding, gives the location of its fix and, if only part was accepted, identifies the accepted claim to judge. The full report stays in the round's findings file. A cross-family reviewer that runs as a command, and a reviewer that cannot be resumed, gets a new run of the same reviewer with this prompt. The resumed same-model reviewer confirms a manual-fallback reviewer's fixes and any the cross-family reviewer could not confirm, using the same selection and the actual source key, for example `cross-family-2:F<n>`. In a code review each goes to the resumed reviewer of its axis. This is the single automatic confirmation round.
- **Follow-up**: a gate's follow-up round ([D007§follow-up-round: follow-up round](D007-change-tiers.md#follow-up-round)) takes a review snapshot once the new revisions are made, keeping its id in the round's own `snapshot.txt`, and gives each of the gate's reviewers the follow-up prompt of the `canon-blind-review` skill. The prompt asks for a review of what changed, at the gate's tier and with the first-round prompt's criteria and rules, reading the rest of the repository for context as that prompt allows, reported as in a first round with findings numbered from F1, and uses the baseline for each reviewer and target defined by [D007§follow-up-round: follow-up round](D007-change-tiers.md#follow-up-round). Group paths that share a verified baseline in a diff to the new snapshot. Save the actual diff commands with their prompts. When the follow-up has no single verified baseline, omit the shared baseline pin so [D001§first-round-review-input: retained input](../../designs/D001-skill-telemetry.md#first-round-review-input) stays unknown. When the last covered input cannot be established or the diff fails, name the revised sections for that reviewer to read. A reviewer that runs as a host subagent is resumed by its id; a cross-family reviewer that runs as a command, and one that cannot be resumed, gets a new run, given its first-round prompt followed by the follow-up prompt; a manual-fallback reviewer’s part on a previously covered target goes to the resumed same-model reviewer. When the earlier pass was waived or a new target lacks independent coverage, apply [D007§target-coverage: target coverage](D007-change-tiers.md#target-coverage). Fixes of the round's accepted blocker and major findings are confirmed as above, from the round's own snapshot.
- **Targeted recheck**. On a separate request, take a snapshot of the version to check. Use the scoped confirmation prompt for the named source finding and accepted claim, citing the fix and the diff from that reviewer’s last checked snapshot, or the locations alone when no diff is available. Resume that reviewer when possible. A command or unavailable session gets a fresh run of the same reviewer. Identify a delegate explicitly and apply the confirmation fallback. Save the prompt, terminal report, run ID and the checked snapshot under a fresh report stem as [D001§review-files: review files](../../designs/D001-skill-telemetry.md#review-files) specifies. The result is separate from the first confirmation.
- **Workers**: a worker blocked on a question that the session settles with the `canon-grill` triage is resumed with the answer, and one blocked on a plan problem with one clear fix is resumed after the session edits and logs the plan. A worker that cannot be resumed is replaced by a new one, given the worker prompt followed by the answer when it was blocked on a question. Before a new worker replaces one, the session stashes the slice's changes, new files included, under a message that starts with the plan's id and the slice, `<P id> S<n>`, and names the replacement, and logs that message, so the new worker starts from the slice's start, in the trace unit that [D001§call-sites: call sites](../../designs/D001-skill-telemetry.md#call-sites) gives it. A question only the user can answer, a plan problem without such a fix, any design problem and a `stuck` report pause the slice; a stuck worker is not retried. A paused slice keeps its changes, new files included, in a stash whose message starts with `<P id> S<n>`, logged with its problem in the plan's Log, for whoever resumes it. A stash is found by its message, never by its `stash@{<n>}` position.

### Review snapshots

`canon.py review start` from [D007§checking-required-review-coverage: coverage checks](D007-change-tiers.md#checking-required-review-coverage) creates a fresh worktree-local directory under `.canon/canon-blind-review/TOPIC/` and prints its path. A follow-up can use `TOPIC/followup-N`. Keep its declared kind, tier, targets, requested roles and optional `--unit TRACE_ID` in `round.json`. Use `--base REF` for a diff, or `none` for a full-document gate. Pin the full commit behind each unambiguous baseline in the review store, including project objects. With `--snapshot COMMIT` use the exact prepared target, otherwise take a fresh snapshot. Report any unavailable input and use the established full-document or no-diff fallback where applicable. For a replacement, explicitly carry forward only verified matching input material. Dispatch every new reviewer into the new directory, so an old job finishing late writes to its own directory. Keep source reports, confirmations and optional telemetry attached to the round that produced them.

`canon.py snapshot` records the work tree for a confirmation's diff and prints the snapshot commit's full id, whether tracing is on or off.

```text
.canon/canon/snapshots/.git            review snapshot repository: refs/snapshots/<id> per snapshot
.canon/canon/snapshots/snapshot.lock   held by each call
```

- The repository lives in `.canon/canon/snapshots/` at the checkout's root, found as [D001§switch-and-storage: switch and storage](../../designs/D001-skill-telemetry.md#switch-and-storage) finds that root, so every linked worktree has its own, one in `.worktrees/` included; the diff command runs from that root. It is built on first use as the trace one is, and each call writes `.canon/canon/.gitignore` when it is missing, as `trace start` does. Nothing is written in `.canon/canon/trace/`, so tracing off still writes nothing there.
- It takes the snapshot as [D001§snapshots: snapshots](../../designs/D001-skill-telemetry.md#snapshots) takes a trace snapshot, with no parent, in this repository instead of the trace one and at `refs/snapshots/<id>`, where `<id>` is the UTC time and 6 random hex digits. The snapshot holds what `git add -A` would record, and the project is left as a trace snapshot leaves it. Step 5 is skipped: each call writes the absolute path of the project's object directory, as `git rev-parse --git-path objects` names it, to the repository's `objects/info/alternates`, so a snapshot stores only the objects the project lacks and the first one copies no tree. A snapshot that reaches an object the project has since pruned no longer diffs, and the repository's `gc --auto` fails, unreported, until that snapshot expires.
- The repository is scratch. Each call, holding `snapshot.lock`, first deletes, best-effort, the refs of snapshots taken more than 30 days ago and the index copies and `.init-<id>` directories that interrupted calls left more than an hour ago; step 6's `gc --auto` reclaims the space once enough packs or loose objects accumulate. Deleting the directory loses only the diffs of open reviews.
- A call that records no snapshot prints `snapshot error: <reason>`, a reason as [D001§event-lines: event lines](../../designs/D001-skill-telemetry.md#event-lines) defines, with `alternates` and `gitignore` as the steps that write the repository's alternates and `.canon/canon/.gitignore`, followed on standard error by Git's message when there is one, and exits 1: outside Git, when the untracked and unstaged files total more than 10 MiB, after 5 s waiting for `snapshot.lock`, or when a step fails. Such a failure leaves the confirmation without a diff.

## Decisions

- Machine-local routes expose activity, early identity and same-session recovery where supported. Silk had a buffered review lasting nearly 15 minutes and a separate caller deadline that required manual recovery. [R004: Silk feedback](../reviews/R004-silk-canon-field-feedback.md)

- Subagents are new, never forks of the session: a fork carries the conversation, which would unblind a reviewer and fill a worker's context window (`canon-blind-review`'s definition of a blind reviewer; e71dae1). The rule covers the subagents other skills launch too, since a fork would carry the session's assumptions into a researcher, a search or designs meant to differ, and some hosts fork by default, Codex for one (mattpocock/skills 7739eae).
- Subagents run on the session's model and effort, which the user sets: in Cursor a Task subagent runs on the session's model unless the user asks for another, from a fixed list whose names fix the effort, so workers and same-model reviewers need no setup (README, Host verification). It replaced per-role effort tables and the Reviewers and Workers lines (3c560ed).
- A confirmation resumes a reviewer that runs as a host subagent, so it judges the fixes against its own findings (3c94281), and reruns a cross-family reviewer that runs as a command, which needs no per-tool session handling (6ac41ad). Each confirmation prompt carries only the assigned findings and the accepted claim of a split finding, since sending the whole report reopened a declined finding (R004-F8). Findings whose reviewer cannot confirm them, a manual-fallback reviewer's included, go to the resumed same-model reviewer, so the user relays nothing a second time (`canon-blind-review`).
- A confirmation diffs two snapshots of the work tree, taken before the review and after its fixes: work not yet committed has no commit to diff from, and a `git diff` from HEAD mixes the change under review with its fixes. The gates of D001, P001, P002 and D000 each needed an ad-hoc copy or a full reread instead (2026-10-15 to 2026-10-23), and copies of each reviewed file (r3) needed their own rules for untracked, created and deleted files. The snapshots reuse trace's, which record untracked files and add no file to the project's `.git`, read-only in Codex's sandbox, and live outside the trace directory, which tracing off leaves untouched (2026-10-29).
- Review snapshots borrow the project's objects instead of copying them as trace's do: they serve a review for days, so a checkout's first review need not copy the whole tree, 45 MiB in a 20,000-file checkout ([D001§snapshots: snapshots](../../designs/D001-skill-telemetry.md#snapshots)), and a snapshot whose objects the project prunes loses only its diff.
- Reports come in the documentation language and are saved verbatim: a user's rule to reply in Simplified Chinese reached the reviewers, and sessions saved translations or summaries whose originals survived only in the subagents' transcripts ([R003: Silk design phase](../reviews/R003-silk-design-phase.md), F4).
- Reviewers run in the foreground when the session has nothing else to do, and a session checks whether a reviewer's report is saved before acting on its notice and looks in the host's record while a notice is overdue: a host delivered a notice again, late, after the session had merged that report, and another sent none for a finished confirmation, so the session idled until the user asked (R003-F12; D001 r8's confirmation, 2026-11-05).
- `canon-blind-review` is the one place for the rules every blind review shares: they were restated in up to four skill files, so one rule change edited three to six of them ([R001: Codebase review of the canon module](../reviews/R001-canon-module.md), F3; b387f60, 869e499, 98ab39c).
- While reviewers read, the session leaves the work tree alone instead of reviewers reading a checkout of the snapshot, which would cost a full checkout per review and lack the history `check` reads: an author edited while a reviewer still read, then counted its approve as covering those edits ([R003§r003-f5-reviewers-read-the-live-work-tree: R003-F5](../reviews/R003-silk-design-phase.md#r003-f5-reviewers-read-the-live-work-tree)). Other sessions keep out of the work tree by working in linked worktrees of their own ([D006§concurrent-work: concurrent work](../../designs/D006-doc-model.md#concurrent-work)).
- Reviewers write no scratch files, and workers keep theirs in `.canon/canon-implement/`: a gate reviewer and a code reviewer each left one in the tree under review, and a worker given no place wrote its benchmarks to `/tmp`, where every write waited for the user's approval (2026-10-23).
- The reviewer file lives in the user's config directory, beside the trace switch ([D001§switch-and-storage: switch and storage](../../designs/D001-skill-telemetry.md#switch-and-storage)), outside every checkout: the tools and logins its reviewers rely on differ between machines but not between checkouts, and a file in each checkout's `.canon/` sent every clone and linked worktree to the manual fallback (6ac41ad; R001-F7; the user's decision, 2026-11-11).
- A missing reviewer is set up from the user's first answer, a family without one is recorded as `none`, and each family lists its reviewers in fallback order: without a file, each L2 gate of a project rediscovered the reviewer from old transcripts or asked the user again, and the setup re-asked in every run of `canon-init` (R003-F3, D004 gate; the user's decision, 2026-11-11). Reviewers are listed per session family because one global order cannot express a preference such as Claude sessions to GPT, GPT to Gemini and Gemini to Claude.
- Codex resumes a subagent with `send_input` to its agent id, and `resume_agent` reopens a closed one (openai/codex 5228d94, `codex-rs/core/src/tools/handlers/multi_agents_spec.rs`).
- A stuck worker's slice pauses for the user instead of being retried: a94fe18 made workers inherit the session's effort, which left no higher effort to retry at.
- A subagent whose run stopped gets one more run, resumed when it can be: a new one starts the work over, as a replaced reviewer did in D002's gate before the user asked for resuming, while the resumed one finished that review (2026-10-22). A second stop ends the attempts, since a stop that repeats, such as a hanging test or a full context, would otherwise loop.
- A replacement worker starts from the slice's start, its predecessor's changes stashed: a half-built tree would give the new worker a wrong baseline for the tests it must keep green.
- A stash message starts with the plan's id as well as the slice, and the stash is found by its message: every linked worktree of a repository shares one stash list, so with sessions in worktrees of their own ([D006§concurrent-work: concurrent work](../../designs/D006-doc-model.md#concurrent-work)) another session's stash shifts the `stash@{<n>}` positions, and another plan's paused slice can have the same number (2026-11-13).
