# E002: Ideas from popular agent skill libraries

## Question

Which ideas from the most widely used public agent-skill libraries could canon absorb? First, which libraries are most widely used, by GitHub stars and, where published, install counts such as the [skills.sh](https://skills.sh) leaderboard of `npx skills` or a host's plugin marketplace, on the research date. Then, for at least the five most used, including [anthropics/skills](https://github.com/anthropics/skills), [obra/superpowers](https://github.com/obra/superpowers) and [mattpocock/skills](https://github.com/mattpocock/skills), whose earlier versions canon's ported execution skills come from (each ported skill's `NOTICE` names its upstream skill): which skills, workflow mechanics and skill-authoring practices do something that canon's skills (the Skills tables of the [README](../../README.md)) and backlog ([C001: Canon backlog](../concepts/C001-canon-backlog.md), [C002: Acceptance check of a finished change](../concepts/C002-acceptance-check.md)) lack, or do differently in a way that could improve canon?

It is answered by a ranked shortlist of candidate ideas, each with its source skill files at a pinned tag or commit, what it does in one or two sentences, canon's nearest equivalent (a skill name or none), how it would serve canon's goals in [D000: Project overview](../designs/D000-project-overview.md) (long-running work carried across sessions and models), its cost in context, subagents and user interruptions, and the doc that would take it up: an existing design, C001, C002 or a new design topic. Ideas canon already has, and ideas that conflict with D000's Decisions or the Skill rules of [AGENTS.md](../../AGENTS.md), are listed briefly with the reason they are left out. The shortlist feeds C001, and C002 where it bears on checking that a finished change works.

### obra/superpowers (v7.0.2)

- Skill authoring is test-driven: "You write test cases (pressure scenarios with subagents), watch them fail (baseline behavior), write the skill (documentation), watch tests pass (agents comply), and refactor (close loopholes)", under the rule "NO SKILL WITHOUT A FAILING TEST FIRST", which covers edits too ([writing-skills/SKILL.md L10-L17, L164-L170](https://github.com/obra/superpowers/blob/v7.0.2/skills/writing-skills/SKILL.md?plain=1#L10-L17)). Before full scenarios it micro-tests wording: one fresh-context sample per call with the realistic surrounding prompt, always a no-guidance control ("If the control doesn't exhibit the failure, there is nothing to fix"), 5 or more repetitions per variant, every flagged match read by hand, and variance treated as a metric ([L295-L306](https://github.com/obra/superpowers/blob/v7.0.2/skills/writing-skills/SKILL.md?plain=1#L295-L306)). Canon's authoring reference, [canon-agent-writing](../../skills/execution/canon-agent-writing/SKILL.md), says the no-op test "is model-relative ... settle it by running the document, not by debate", but gives no procedure for running it; `validate.py` checks structure and text budgets, and the README's [Host verification](../../README.md#host-verification) is a manual checklist with one implicit-invocation probe.
- "Match the Form to the Failure": classify the baseline failure first; a rule skipped under pressure takes a prohibition, a rationalization table and red flags, while an output of the wrong shape takes a positive recipe, since "In head-to-head wording tests on dispatch-prompt guidance, the prohibition arm produced clearly more of the unwanted content than the recipe arm ... and trended worse than even the no-guidance control"; nuance and exemption clauses degraded a winning recipe ([writing-skills/SKILL.md L249-L263](https://github.com/obra/superpowers/blob/v7.0.2/skills/writing-skills/SKILL.md?plain=1#L249-L263)). Canon's [canon-agent-writing§leading-words](../../skills/execution/canon-agent-writing/SKILL.md#leading-words) says the same of shaping ("Prompt the positive") but allows a prohibition only "as a hard guardrail you cannot phrase positively", with no case for discipline failures. The test data behind superpowers' claim is not published in the skill. Excerpt of these sections and the description rule below: [E002/superpowers-writing-skills.md](E002/superpowers-writing-skills.md).
- A description says only when to use the skill: "It never summarizes the skill's workflow, because an agent that reads a workflow summary follows it instead of reading the skill" ([writing-skills/SKILL.md L95-L98](https://github.com/obra/superpowers/blob/v7.0.2/skills/writing-skills/SKILL.md?plain=1#L95-L98)). The evidence given is one observed case: a description saying "code review between tasks" made an agent do one review where the skill's flowchart showed two, and a description of triggers alone fixed it ([references/discovery.md L63-L71](https://github.com/obra/superpowers/blob/v7.0.2/skills/writing-skills/references/discovery.md?plain=1#L63-L71)). Canon's auto skills put a workflow summary after their triggers, for example `canon-investigate`'s "Builds a red-capable feedback loop, ranks falsifiable hypotheses from the evidence, instruments, then fixes with a regression test" ([canon-investigate/SKILL.md](../../skills/execution/canon-investigate/SKILL.md)); AGENTS.md's Skill rules ask for one short sentence of what the skill does, then the triggers, and do not ask for that summary ([AGENTS.md](../../AGENTS.md)).
- Completion claims need fresh evidence: "NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE ... If you haven't run the verification command in this message, you cannot claim it passes", with a table of claims and what proves each, including "Agent completed: VCS diff shows changes; Not sufficient: Agent reports 'success'" and "Requirements met: Line-by-line checklist; Not sufficient: Tests passing" ([verification-before-completion/SKILL.md L16-L48](https://github.com/obra/superpowers/blob/v7.0.2/skills/verification-before-completion/SKILL.md?plain=1#L16-L48)). Canon already has the delegation part: `canon-implement` re-runs a done slice's tests and checks its diff ([canon-implement§2-each-slice](../../skills/execution/canon-implement/SKILL.md#2-each-slice)), and `canon-tdd` defines done ([canon-tdd§done](../../skills/execution/canon-tdd/SKILL.md#done)). The requirements line is what [C002: Acceptance check](../concepts/C002-acceptance-check.md) proposes.
- Subagent-driven development keeps a ledger file per plan in a git-ignored workspace because "Conversation memory does not survive compaction. In real sessions, controllers that lost their place have re-dispatched entire completed task sequences — the single most expensive failure observed" ([subagent-driven-development/SKILL.md L108-L128](https://github.com/obra/superpowers/blob/v7.0.2/skills/subagent-driven-development/SKILL.md?plain=1#L108-L128)). Canon keeps the same state in the plan itself, committed after each slice ([canon-implement§2-each-slice](../../skills/execution/canon-implement/SKILL.md#2-each-slice)).
- "Rulings, not stalls": the controller decides conflicts, ambiguities and plan defects itself, records each as `Ruling: <what you decided> — <why> — <what it costs if wrong>`, and stops only for an irreversible or destructive operation, a security-sensitive action, a side effect outside the worktree such as a merge, push or publish, or a plan so broken that every path is a guess ([subagent-driven-development/SKILL.md L15-L31](https://github.com/obra/superpowers/blob/v7.0.2/skills/subagent-driven-development/SKILL.md?plain=1#L15-L31)). Canon edits a plan problem with one clear fix without asking, but pauses the slice for a decision the docs do not settle or a design problem and finishes the independent slices first ([workflow.md§implementation](../../skills/governance/canon/workflow.md#implementation), [canon-grill§done](../../skills/execution/canon-grill/SKILL.md#done)).
- Model per role: "Use the least powerful model that can handle each role"; a cheap model for mechanical one- or two-file tasks with complete specs, a standard one for integration, the most capable for architecture and the final whole-branch review, reviewers scaled to the diff's size and risk, "Always specify the model explicitly", and "Turn count beats token price ... the cheapest models routinely take 2-3× the turns on multi-step work", so a mid-tier model is the floor for reviewers ([subagent-driven-development/SKILL.md L140-L174](https://github.com/obra/superpowers/blob/v7.0.2/skills/subagent-driven-development/SKILL.md?plain=1#L140-L174)). Canon launches workers and same-model reviewers without a model so they inherit the session's ([workflow.md§subagents](../../skills/governance/canon/workflow.md#subagents)); [C001: Canon backlog](../concepts/C001-canon-backlog.md)'s **How strong a reviewer needs to be** asks the open question.
- Context hygiene for the controller: "Everything you paste into a dispatch prompt — and everything a subagent prints back — stays resident in your context ... Hand artifacts over as files"; the implementer writes its full report to a named file and returns only status, commits, a one-line test summary and concerns; "a real session's dispatch hit 42k chars of which 99% was pasted history"; and the implementer never dispatches subagents, since "every reviewer a worker spawned duplicated the task review" ([subagent-driven-development/SKILL.md L183-L230](https://github.com/obra/superpowers/blob/v7.0.2/skills/subagent-driven-development/SKILL.md?plain=1#L183-L230)). Canon's worker prompt already passes paths and nothing else, but the worker's final message is its whole report, which stays in the orchestrator's context for every later slice ([canon-implement§worker-prompt](../../skills/execution/canon-implement/SKILL.md#worker-prompt)); reviewer reports are saved to files but also read in full ([canon-blind-review§review-files](../../skills/execution/canon-blind-review/SKILL.md#review-files)).
- Superpowers reviews every task (spec compliance and code quality) and then the whole branch ([subagent-driven-development/SKILL.md L253-L259](https://github.com/obra/superpowers/blob/v7.0.2/skills/subagent-driven-development/SKILL.md?plain=1#L253-L259)); canon deliberately reviews only the finished change: "Plan slices are not reviewed one by one" ([workflow.md§code-review](../../skills/governance/canon/workflow.md#code-review)).
- Receiving review: "READ ... UNDERSTAND ... VERIFY: Check against codebase reality ... EVALUATE ... RESPOND: Technical acknowledgment or reasoned pushback ... IMPLEMENT: One item at a time, test each"; for external reviewers, check that the suggestion is correct for this codebase, breaks nothing, and that the reviewer had the context, push back with technical reasoning, and grep for actual usage before "implementing properly" ([receiving-code-review/SKILL.md L17-L26, L67-L96](https://github.com/obra/superpowers/blob/v7.0.2/skills/receiving-code-review/SKILL.md?plain=1#L17-L26)). Canon's merge step says only "Accept and fix each finding, decline it with a one-line reason for the user, or escalate it to the user. A finding raised by two reviewers is accepted unless it is clearly wrong" ([canon-blind-review§merge](../../skills/execution/canon-blind-review/SKILL.md#merge)).
- Finishing a branch: run the full suite, detect a worktree or detached HEAD, confirm the base branch, offer exactly "Merge back to <base-branch> locally", "Push and create a Pull Request" or "Keep the branch as-is", re-run the tests on the merged result before removing anything, then clean up the worktree by provenance ([finishing-a-development-branch/SKILL.md L10-L111](https://github.com/obra/superpowers/blob/v7.0.2/skills/finishing-a-development-branch/SKILL.md?plain=1#L10-L111)). Canon leaves merging back, `git worktree remove` and deleting the branch "the user's to do, or yours when the user asks" ([canon§concurrent-work](../../skills/governance/canon/SKILL.md#concurrent-work)).
- Bootstrap by hook: the plugin's `SessionStart` hook (matcher `startup|clear|compact`) injects the full text of `using-superpowers`, which says "If you think there is even a 1% chance a skill might apply ... you ABSOLUTELY MUST invoke the skill" ([hooks/hooks.json](https://github.com/obra/superpowers/blob/v7.0.2/hooks/hooks.json), [hooks/session-start](https://github.com/obra/superpowers/blob/v7.0.2/hooks/session-start), [using-superpowers/SKILL.md L10-L20](https://github.com/obra/superpowers/blob/v7.0.2/skills/using-superpowers/SKILL.md?plain=1#L10-L20)). Canon reaches agents through the `AGENTS.md` canon block and auto skill descriptions, and ships through `npx skills`, which installs skill directories only ([README](../../README.md#install)).
- Session forensics: `diagnosing-superpowers` locates a session's transcripts on disk, then dispatches one analyst subagent per dimension in parallel (skill timeline, plan adherence, repeated work, stumbles, quality evidence, request conflicts, cost and time), discards every finding without a `path:line` citation into the transcript, and fills a report and, on approval, an issue for the maintainers ([diagnosing-superpowers/SKILL.md L8-L44](https://github.com/obra/superpowers/blob/v7.0.2/skills/diagnosing-superpowers/SKILL.md?plain=1#L8-L44)). Canon's nearest are `canon-retro`, which may search a named transcript "with bounded matches" and logs canon's own friction to `skills.jsonl` ([canon-retro§1-find-events](../../skills/execution/canon-retro/SKILL.md#1-find-events)), and tracing, which records events but "never prompts, outputs, source code or free text" ([README§tracing](../../README.md#tracing)).

### anthropics/skills (2c5958e)

- `skill-creator` evaluates a skill against a baseline: for each of 2-3 realistic prompts it spawns, in the same turn, a run with the skill and a baseline run (no skill for a new skill, a snapshot of the old version for an edit), drafts assertions while they run, saves each run's `total_tokens` and `duration_ms`, grades assertions with a grader subagent or a script, and aggregates `benchmark.json` with pass rate, time and tokens per configuration as mean ± stddev and the delta; an analyst pass flags "assertions that always pass regardless of skill (non-discriminating), high-variance evals (possibly flaky), and time/token tradeoffs" ([skill-creator/SKILL.md L141-L236](https://github.com/anthropics/skills/blob/2c5958ecac7cee2b583967a2c4981d0f4a75c579/skills/skill-creator/SKILL.md?plain=1#L141-L236)). Comparing a skill to the no-system-prompt baseline conflates the skill with the generic terseness ask, which is what an earlier version of this harness did and is why its numbers were inflated" ([evals/README.md L9-L20](https://github.com/JuliusBrussee/caveman/blob/ad473752bdc86ca96d7289443228d4c53ec119a8/evals/README.md?plain=1#L9-L20)). Each `claude -p` call is isolated with `--setting-sources project --strict-mcp-config --disable-slash-commands --no-session-persistence` from an empty directory, so installed plugins, hooks, skills and `CLAUDE.md` reach no arm, and the snapshot is committed so CI reads it for free ([L37-L53](https://github.com/JuliusBrussee/caveman/blob/ad473752bdc86ca96d7289443228d4c53ec119a8/evals/README.md?plain=1#L37-L53)).
- Measured from the committed snapshot (10 prompts, `claude-opus-5-5`, Claude Code 2.1.288, generated 2026-10-02; [evals/snapshots/results.json](https://github.com/JuliusBrussee/caveman/blob/ad473752bdc86ca96d7289443228d4c53ec119a8/evals/snapshots/results.json)), median reply lengths in characters are 2,713 with no prompt, 1,675 with the terse control, 1,673.5 with `caveman`, 1,153 with `ultracave` and 615.5 with `megacave` (Classical Chinese). These medians are this survey's own count of characters, not the repository's token table, which needs tiktoken; inference: on this model the main `caveman` skill adds almost nothing over a one-line "Answer concisely.", and only the more extreme styles shorten replies further. No fidelity snapshot is committed, so whether the facts survive is unmeasured ([evals/README.md L161-L191](https://github.com/JuliusBrussee/caveman/blob/ad473752bdc86ca96d7289443228d4c53ec119a8/evals/README.md?plain=1#L161-L191)).
- `cavecrew` gives three subagent presets fixed output contracts, an investigator that returns `path:line — symbol — note` rows or `No match.`, a builder that returns the edited range and a re-read check or a terminal token such as `too-big.`, and a reviewer that returns one `path:line` line per finding or `No issues.`, because "Subagent tool results get injected into main context verbatim ... Across 20 delegations in one session that's the difference between context exhaustion and finishing the task"; the main thread never accepts or rejects an absence claim such as `No issues.` "without one targeted check" ([cavecrew/SKILL.md L9-L74](https://github.com/JuliusBrussee/caveman/blob/ad473752bdc86ca96d7289443228d4c53ec119a8/skills/cavecrew/SKILL.md?plain=1#L9-L74)). Canon's reviewer prompt already fixes a finding format and asks that each be "as short as it can be while a reader can understand and verify it" ([canon-blind-review§prompt](../../skills/execution/canon-blind-review/SKILL.md#prompt)); its worker report lists fields but sets no length or shape ([canon-implement§worker-prompt](../../skills/execution/canon-implement/SKILL.md#worker-prompt)).
- `caveman-compress` rewrites a memory file such as `CLAUDE.md` in caveman style to save input tokens, keeping a readable backup, validating the result and retrying fixes up to twice ([caveman-compress/SKILL.md L1-L40](https://github.com/JuliusBrussee/caveman/blob/ad473752bdc86ca96d7289443228d4c53ec119a8/skills/caveman-compress/SKILL.md?plain=1#L1-L40)). `verify-and-stop` turns acceptance conditions into "smallest sufficient proof set", distinguishes "pass, fail, unavailable, and blocked exactly", edits no product code, and stops once the proof is complete ([verify-and-stop/SKILL.md L8-L16](https://github.com/JuliusBrussee/caveman/blob/ad473752bdc86ca96d7289443228d4c53ec119a8/skills/verify-and-stop/SKILL.md?plain=1#L8-L16)), the verdict set [C002: Acceptance check](../concepts/C002-acceptance-check.md)'s scenarios would need for an artifact the subagent cannot run.

## Conclusion

On 2026-11-13 the most used general-purpose skill libraries are mattpocock/skills, obra/superpowers, affaan-m/ECC and anthropics/skills, then JuliusBrussee/caveman and addyosmani/agent-skills. mattpocock/skills leads on both measures (323,451 stars, 32.9M skills.sh installs); superpowers (317,038 stars) and ECC (302,251) nearly match it in stars but have far fewer skills.sh installs (3.9M and 1.7M), and superpowers has 1.0M more on the Claude Marketplace, where only Anthropic's `frontend-design` has more. Cursor publishes no counts.

What canon could take from them is mostly ways to **measure** skills, which canon lacks entirely: evals against a baseline, trigger tests for descriptions, and wording tests. Second come a few cheap review and reporting rules for unattended work. The ranked shortlist, highest value for D000's goals per unit of cost first:
