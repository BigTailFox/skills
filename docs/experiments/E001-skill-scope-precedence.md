# E001: Precedence of project and user skills across hosts

## Question

When a skill of the same name is installed both for the user (such as `~/.agents/skills/canon`, `~/.claude/skills/canon` or `~/.cursor/skills/canon`) and in a project (such as `<repo>/.agents/skills/canon`, `<repo>/.claude/skills/canon` or `<repo>/.cursor/skills/canon`), which one does each of Cursor, Claude Code and Codex load? Which project directories does each read skills from, and does a project install by `npx skills` (vercel-labs/skills 1.8) land where each reads?

It is answered by each host's documented or source-confirmed rule, with the version or date it holds for: the project's skill wins, the user's wins, both load, or the rule is unstated. It decides whether [D004: Project setup](../designs/D004-project-setup.md) can recommend a project install pinned to a release, so that each project runs the canon version it pins even where the user also has the skills installed for every project.

## Results

### `npx skills` 1.8.1 project install

- The CLI's agent table gives Claude Code the project directory `.claude/skills/` and the user directory `~/.claude/skills/`, Codex `.agents/skills/` and `~/.agents/skills/`, and Cursor `.agents/skills/` and `~/.cursor/skills/` ([docs/agents.md](https://github.com/vercel-labs/skills/blob/v1.8.1/docs/agents.md)); the source agrees: `claude-code` has `skillsDir: '.claude/skills'` and `globalSkillsDir` `$CLAUDE_CONFIG_DIR/skills` (default `~/.claude/skills`), `codex` has `.agents/skills` and `~/.agents/skills`, `cursor` has `.agents/skills` and `~/.cursor/skills` ([src/agents.ts L166-L287](https://github.com/vercel-labs/skills/blob/v1.8.1/src/agents.ts#L166-L287)).
- An agent whose `skillsDir` is `.agents/skills` is "universal"; without `-g`, its install directory is the canonical `<cwd>/.agents/skills/` ([src/installer.ts L117-L148](https://github.com/vercel-labs/skills/blob/v1.8.1/src/installer.ts#L117-L148)). So for Codex and Cursor a project install lands in `<repo>/.agents/skills/<name>` and nowhere else.
- For a non-universal agent such as Claude Code, the symlink mode (the default when the targets span more than one directory) first copies the skill to `<cwd>/.agents/skills/<name>` and then links `<cwd>/.claude/skills/<name>` to it, falling back to a copy when the link fails ([src/installer.ts L309-L494](https://github.com/vercel-labs/skills/blob/v1.8.1/src/installer.ts#L309-L494)). Claude Code sets `createProjectSkillsDirByDefault: true`, so the link is made even when the project has no `.claude/` yet ([src/agents.ts L166-L176](https://github.com/vercel-labs/skills/blob/v1.8.1/src/agents.ts#L166-L176), [src/installer.ts L84-L101](https://github.com/vercel-labs/skills/blob/v1.8.1/src/installer.ts#L84-L101)); other non-universal agents are skipped when their project root directory is missing.
- When every target shares one directory, `defaultInstallMode` picks copy mode, which copies straight into the agent's directory ([src/add.ts L474-L480](https://github.com/vercel-labs/skills/blob/v1.8.1/src/add.ts#L474-L480), [src/installer.ts L380-L389](https://github.com/vercel-labs/skills/blob/v1.8.1/src/installer.ts#L380-L389)); for Codex or Cursor alone that directory is again `<repo>/.agents/skills/<name>`.
- `npx skills add <repo> -s <name> -y` without `--agent` picks its targets this way: run inside a detected coding agent, it takes that agent plus every universal agent ([src/add.ts L2386-L2397](https://github.com/vercel-labs/skills/blob/v1.8.1/src/add.ts#L2386-L2397); Cursor needs `CURSOR_AGENT` or `CURSOR_EXTENSION_HOST_ROLE=agent-exec`, Claude Code maps to `claude-code`, Codex to `codex`, [src/detect-agent.ts L7-L54](https://github.com/vercel-labs/skills/blob/v1.8.1/src/detect-agent.ts#L7-L54)); otherwise every agent whose config directory exists (`~/.claude` or `$CLAUDE_CONFIG_DIR` for Claude Code, `~/.codex`, `$CODEX_HOME` or `/etc/codex` for Codex, `~/.cursor` for Cursor) plus every universal agent, or all agents when none is detected ([src/add.ts L2762-L2800](https://github.com/vercel-labs/skills/blob/v1.8.1/src/add.ts#L2762-L2800), [src/agents.ts L166-L287](https://github.com/vercel-labs/skills/blob/v1.8.1/src/agents.ts#L166-L287)). Without `-g` and with `-y`, scope is the project: `installGlobally` defaults to `false` and the scope prompt runs only without `-y` ([src/add.ts L2858-L2876](https://github.com/vercel-labs/skills/blob/v1.8.1/src/add.ts#L2858-L2876)). Cursor and Codex are universal, so they are always among the targets; Claude Code is one when it is the running agent or `~/.claude` exists.
- The docs state the same layout: "The `.agents/skills/` directory is the shared location. Selecting Claude Code also creates links under `.claude/skills/` pointing to the shared skills" ([docs/commands.md L302-L303](https://github.com/vercel-labs/skills/blob/v1.8.1/docs/commands.md?plain=1#L302-L303), said of `experimental_sync`). Its scope table gives the project location only generically as `./<agent>/skills/` ([docs/commands.md L114-L119](https://github.com/vercel-labs/skills/blob/v1.8.1/docs/commands.md?plain=1#L114-L119)).
- Conflict between the CLI's docs and its source, for `-g` only: `docs/agents.md` lists Cursor's global path as `~/.cursor/skills/`, but a universal agent whose `globalReadsCanonical` is not `false` (Cursor and Codex both) installs globally to the canonical `~/.agents/skills/<name>` and makes no link in the agent's own global directory ([src/installer.ts L430-L440](https://github.com/vercel-labs/skills/blob/v1.8.1/src/installer.ts#L430-L440), [src/installer.ts L140-L148](https://github.com/vercel-labs/skills/blob/v1.8.1/src/installer.ts#L140-L148)). So `npx skills add … -g` puts a Cursor skill in `~/.agents/skills/`, not `~/.cursor/skills/`.

### Pinning and restoring with `npx skills` 1.8.1

- `add` pins a release tag or a full commit after `@`: "Pin a release tag or full commit. Skill names still use the same @ form", with the example `npx skills add owner/repo@v1.2.3 --skill my-skill` ([docs/commands.md L21-L22](https://github.com/vercel-labs/skills/blob/v1.8.1/docs/commands.md?plain=1#L21-L22)).
- Run on 2026-11-12 from a Cursor agent in a scratch repository, `npx skills add BigTailFox/skills@v0.5.1 -s canon -y` filled `.agents/skills/canon/` and wrote a version 2 `skills-lock.json` whose `canon` entry holds `"source": "BigTailFox/skills"`, `"ref": "v0.5.1"`, `"sourceType": "github"`, the `skillPath` and a `computedHash`. It made no `.claude/skills/` link, as the target rule above predicts for a run inside Cursor.
- `npx skills experimental_install` restores the sources `skills-lock.json` records into `.agents/skills/` and links them into agent directories: to the agents given with `--agent`, else those last selected with `skills add`, else the agents detected on the machine. Skills whose files already match the lock's content hash are kept and only get missing links. With `--frozen-lockfile`, the default when a CI variable such as `CI` is set, every skill must match its recorded hash, and a missing or empty lock is an error ([docs/commands.md L377-L413](https://github.com/vercel-labs/skills/blob/v1.8.1/docs/commands.md?plain=1#L377-L413)). The command's name marks it experimental, so its behavior may change between releases.

### Claude Code

- Claude Code documents its skill locations as enterprise (`.claude/skills/` in the managed settings directory), personal `~/.claude/skills/<skill-name>/SKILL.md`, project `.claude/skills/<skill-name>/SKILL.md`, nested `<subdir>/.claude/skills/`, `--add-dir` directories' `.claude/skills/`, plugins, and skills synced from claude.ai ([Choose where skills load](https://code.claude.com/docs/en/skills#where-skills-live), [excerpt](E001/claude-code-skills-locations.md)). The table names no `.agents/skills/` directory, project or user, and neither the page nor the changelog through 2.1.322 mentions `.agents` ([CHANGELOG.md](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)).
- Project skills load from `.claude/skills/` in the start directory and in every parent up to the repository root; in a linked worktree, only up to the worktree root, falling back on v2.1.277 or later to the main checkout's project skills when the worktree has no `.claude/skills` at its root ([Load skills in monorepos and subdirectories](https://code.claude.com/docs/en/skills#discovery-from-parent-and-nested-directories)).
- Same name in user and project: the personal skill wins. "Two of enterprise, personal, and project: Enterprise over personal, and personal over project. With `deploy` in both `~/.claude/skills/` and the project's `.claude/skills/`, `/deploy` runs the personal one" ([Resolve skills that share a name](https://code.claude.com/docs/en/skills#resolve-skills-that-share-a-name), page fetched 2026-11-12). Only the other cases (a nested skill, an `--add-dir` skill, a plugin skill) keep both available under qualified names.
- A skill folder may be a symlink to a directory elsewhere; Claude Code reads `SKILL.md` from the target and loads it once even when several locations point at the same target ([Choose where skills load](https://code.claude.com/docs/en/skills#where-skills-live)). So the `.claude/skills/<name>` link that `npx skills` makes to `.agents/skills/<name>` loads as a normal project skill.
- Where `npx skills add <repo> -s <name> -y` lands for Claude Code: in `<repo>/.agents/skills/<name>`, with `<repo>/.claude/skills/<name>` linked to it, which is the documented project location (from the CLI findings above). Inference: a user install of the same name in `~/.claude/skills/<name>`, which `npx skills add -g` creates as a link to `~/.agents/skills/<name>` ([src/installer.ts L309-L494](https://github.com/vercel-labs/skills/blob/v1.8.1/src/installer.ts#L309-L494)), shadows the project install in Claude Code.

### Cursor

- Cursor documents four skill directories: project `.agents/skills/` and `.cursor/skills/`, user `~/.agents/skills/` and `~/.cursor/skills/`, and "for compatibility" also `.claude/skills/`, `.codex/skills/`, `~/.claude/skills/` and `~/.codex/skills/` ([Skill directories](https://cursor.com/docs/skills#skill-directories), [Skills help](https://cursor.com/help/customization/skills#how-do-i-create-a-skill)). A `.cursor/skills/` or `.agents/skills/` folder anywhere inside the repository is also picked up and scoped to files under its directory ([Nested skill directories](https://cursor.com/docs/skills#nested-skill-directories)).
- Neither page states what happens when two of these directories hold a skill of the same name ([Agent Skills](https://cursor.com/docs/skills), [Skills help](https://cursor.com/help/customization/skills), both fetched 2026-11-12). The docs leave the rule unstated.
- The code confirms the directories: for each workspace root and for the home directory, Cursor 3.27.22 searches `.cursor/skills`, `.claude/skills`, `.codex/skills`, `.grok/skills` and `.agents/skills`, plus the built-in `~/.cursor/skills-cursor`; the `.claude`, `.codex` and `.grok` ones only while third-party extensibility is on ([excerpt, skill-discovery.js](E001/cursor-3.27.22-skill-discovery.md#skill-discoveryjs-directories-searched)). That setting, labelled "Include Third-Party Plugins, Skills, and Other Configs", defaults to on ([excerpt](E001/cursor-3.27.22-skill-discovery.md#default-of-the-third-party-setting)).
- Same name in user and project: both load. `MergedAgentSkillsService.getAllAgentSkills` merges the skills of every root through `dedupePreferringAgentStore`, whose key is the path before the first `/.cursor/`, `/.claude/`, `/.codex/`, `/.grok/` or `/.agents/` segment joined to the path after it ([excerpt, skill-dedupe.js](E001/cursor-3.27.22-skill-discovery.md#skill-dedupejs-which-same-named-skills-are-merged), [excerpt, agent-skills-service.js](E001/cursor-3.27.22-skill-discovery.md#agent-skills-servicejs-mergedagentskillsservicegetallagentskills-fragment)). So `~/.agents/skills/canon/SKILL.md` and `~/.cursor/skills/canon/SKILL.md` share the key `<home>::skills/canon/SKILL.md` and only the first found is kept, but `<repo>/.agents/skills/canon/SKILL.md` has the key `<repo>::skills/canon/SKILL.md` and is kept beside the user's copy. Nothing in this path compares skill names. The same key also collapses the `<repo>/.claude/skills/<name>` link that `npx skills` makes for Claude Code into the `<repo>/.agents/skills/<name>` entry, so that link adds no duplicate in Cursor (derived from the key function).
- Order: `sortAgentSkillsForPromptOrder` puts built-in skills first, then agent-store skills, then user-home skills, then workspace skills, then plugin skills, keeping discovery order within a tier ([excerpt, agent-skills-prompt-order.js](E001/cursor-3.27.22-skill-discovery.md#agent-skills-prompt-orderjs-order-of-skills-in-the-prompt)). A user `canon` is therefore listed before a project `canon`.
- How the agent tells them apart: the skill message sent to the model service, `agent.v1.AgentSkill`, carries `full_path`, `description` and `content` and no separate name field (field table in the same `daemon.cjs`). Inference: the agent sees two `canon` entries with the same description and different full paths, and nothing marks either as the one to use; which one it reads is up to the model. The prompt itself is assembled by Cursor's service, outside the installed code.
- The `cursor-agent-exec` extension of the same IDE build and the `cursor-agent` CLI 2026.11.11-043ef28 ship the same key function (`<root>::<rest>` from the same five config-directory segments), the same merge that keeps distinct keys, and the same tier order `Builtin, UserStore, UserHome, Workspace, Plugin` (minified `main.js` and `index.js`, read 2026-11-12).
- Where `npx skills add <repo> -s <name> -y` lands for Cursor: `<repo>/.agents/skills/<name>`, a documented project directory (from the CLI findings above). `npx skills add -g` puts the skill in `~/.agents/skills/<name>`, a documented user directory, so a user install and a project install of `canon` both load in Cursor.

### Codex

- Codex documents repository skills in `.agents/skills` of every directory from the working directory up to the repository root (scope `REPO`), user skills in `$HOME/.agents/skills` (`USER`), admin skills in `/etc/codex/skills` (`ADMIN`), and bundled system skills (`SYSTEM`); it follows symlinked skill folders ([Where Codex loads local skills](https://learn.chatgpt.com/docs/build-skills#where-to-save-skills), fetched 2026-11-12).
- Same name in user and project, documented: "If two skills share the same `name`, Codex doesn't merge them; both can appear in skill selectors" ([same section](https://learn.chatgpt.com/docs/build-skills#where-to-save-skills)). "In Codex, the initial list also includes each skill's file path" ([Build skills](https://learn.chatgpt.com/docs/build-skills)).
- The source adds two roots the docs leave out: each project config folder's `.codex/skills` (scope `Repo`) and the deprecated user location `$CODEX_HOME/skills` (default `~/.codex/skills`, scope `User`, "kept for backward compatibility"), next to `~/.agents/skills` (`User`), `$CODEX_HOME/skills/.system` (`System`) and `/etc/codex/skills` (`Admin`) ([host_roots.rs L112-L170](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/ext/skills/src/host_roots.rs#L112-L170)). Repository `.agents/skills` roots come from every directory between the project root (found by the project root markers) and the working directory ([host_roots.rs L176-L392](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/ext/skills/src/host_roots.rs#L176-L392)). Roots are deduplicated by path only ([host_roots.rs L395-L398](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/ext/skills/src/host_roots.rs#L395-L398)).
- Same name, source-confirmed in `rust-v0.167.2`: merging keeps every skill whose `SKILL.md` path differs, dropping only repeats of one path, then sorts by scope (`Repo` 0, `User` 1, `System` 2, `Admin` 3), then name, then path ([host_merge.rs L198-L267](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/ext/skills/src/loader/host_merge.rs#L198-L267)). So a project `canon` and a user `canon` both load, the project one first. The prompt renderer's core-compatible order is `System`, `Admin`, `Repo`, `User`, which again lists the project copy before the user copy ([render.rs L91-L111](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/ext/skills/src/render.rs#L91-L111)), and every entry carries a name, description and path or locator ([catalog_prompt.rs L3-L5](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/ext/skills/src/catalog_prompt.rs#L3-L5)). Nothing tells the model which of two same-named entries to prefer.
- Explicit `$canon` with two enabled skills named `canon`: the core turn path resolves mentions with the `codex-skills` crate, which matches a plain name only when exactly one enabled skill has it ([skills/src/selection.rs L120-L200](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/skills/src/selection.rs#L120-L200), test `collect_explicit_skill_mentions_skips_ambiguous_name` in [selection_tests.rs L226-L240](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/skills/src/selection_tests.rs#L226-L240)), and injects the `SKILL.md` of the skills it selected ([turn.rs L1222-L1248](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/core/src/session/turn.rs#L1222-L1248)). An ambiguous plain `$canon` therefore injects neither copy; picking one in the selector or a linked mention `[$canon](<path>)` selects that path. Conflict inside the source: the skills extension's own resolver instead takes the first enabled catalog entry with the name ([ext/skills/src/selection.rs L65-L76](https://github.com/openai/codex/blob/rust-v0.167.2/codex-rs/ext/skills/src/selection.rs#L65-L76)); which of the two paths runs in a given session was not settled here.
- Where `npx skills add <repo> -s <name> -y` lands for Codex: `<repo>/.agents/skills/<name>`, the documented `REPO` location at the repository root (from the CLI findings above). `npx skills add -g` puts it in `~/.agents/skills/<name>`, the documented `USER` location, so both copies load in Codex.

## Conclusion

No host reliably gives a project's skill precedence over a user's skill of the same name:

- **Claude Code** (docs fetched 2026-11-12, describing versions up to v2.1.319): the user's skill wins, by a documented rule: personal `~/.claude/skills/` over project `.claude/skills/`. It reads project skills only from `.claude/skills/` (start directory up to the repository root, nested ones on demand) and user skills only from `~/.claude/skills/`; it reads no `.agents/skills/`.
- **Cursor** (3.27.22 and `cursor-agent` 2026.11.11, source-confirmed; the docs leave the rule unstated): both load. A user and a project `canon` are separate entries, the user's listed first, told apart only by their full paths, and the model picks one. It reads project `.agents/skills/` and `.cursor/skills/` (nested ones too) and user `~/.agents/skills/` and `~/.cursor/skills/`, plus `.claude/skills/`, `.codex/skills/` and `.grok/skills/` at both levels while third-party configs are on, which is the default.
- **Codex** (docs fetched 2026-11-12 and `rust-v0.167.2` source agree): both load, not merged. The project's copy is listed first and each entry carries its path; a plain `$canon` is ambiguous and, in the core turn path, injects neither copy. It reads `.agents/skills/` in every directory from the working directory up to the repository root and the project's `.codex/skills/`, and user `~/.agents/skills/` plus the deprecated `~/.codex/skills/`.
- **`npx skills add <repo> -s <name> -y` without `-g`** (1.8.1 source) puts the skill in `<repo>/.agents/skills/<name>`, which Cursor and Codex read, and, when Claude Code is a target, links `<repo>/.claude/skills/<name>` to it, which Claude Code reads. So the project install lands where all three read, provided Claude Code is among the targets, which `-a` makes sure of. With `-g` it lands in `~/.agents/skills/<name>`, plus a `~/.claude/skills/<name>` link for Claude Code, so it lands where all three read too. `add <repo>@<tag>` pins the release, `skills-lock.json` records the tag, and `experimental_install` restores it.

For D004, a project install pinned to a release does not guarantee that the project runs the pinned version while the user also has `canon` installed: Claude Code runs the user's copy, and Cursor and Codex offer both and leave the choice to the model. The pinned version is sure to run only where no user install of the same name exists.
