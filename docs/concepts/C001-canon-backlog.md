# C001: Canon backlog

## Motivation

Findings that are not defects of code a design governs, and work that needs a new design first, land here so they stay tracked until a design or an L0 change takes them up.

## Ideas

- **Skills outside canon projects** ([R001: Codebase review of the canon module](../archived/reviews/R001-canon-module.md), F13). A user install of canon writes no docs, since `canon.py` runs only from an install inside the project ([D004§install: install](../designs/D004-project-setup.md#install)), but its auto skills still trigger on generic requests in any repository, and once one runs `canon.py` the agent offers to install canon in a project that never chose it. Where canon is installed but `AGENTS.md` has no canon block, as before `/canon-init`, `new` and `adopt` still create docs and regenerate the index. Scope each auto trigger to projects whose `AGENTS.md` has the canon block with a fallback to the skill's plain discipline, and make `new` and `adopt` refuse without the block. A new topic: `/canon-design`.
- **A design for skill layout and invocation** (R001-F10, F11). AGENTS.md's Skill rules, `agents/openai.yaml` and the trigger modes have no design; neither do the contracts other skills execute: `canon-tdd`'s definition of done and `canon-code-review/smells.md`. Backfill them before they next change; `scripts/validate.py`, which checks the Skill rules, is tooling and needs no backfill ([D000§decisions: decisions](../designs/D000-project-overview.md#decisions)). `canon-review/security.md` counts as a project doc by its name, so the design that takes on `canon-review` lists its exact path.
- **One place for closing a workflow** (R001-F5). The retro end-check paragraph is copied into seven skills and the rule for routing a deferred finding into six; one section in `workflow.md` and one rule beside the known-issue format would replace them.
- **Work-tree snapshots apart from trace** (R001-F6). `canon.py snapshot`, which every confirmation uses, is built from the opt-in trace subsystem's parts; a section of its own, with `trace start` and `snapshot` as its callers, would let either change alone.
- **A faster test suite** (R001-F8). `validate.py` runs the 331 tests in parallel, slowest first, in about 7 s on 24 CPUs, no less than the 5 s three of them wait out canon's lock timeout; but they take about 150 s of CPU time, so a machine with few CPUs still waits. Copying one initialized template repository per test would save about a sixth of it, once the template outlives the single test whose module fixtures `validate.py` sets up for it alone.
- **Check references between skill texts** (R001-F9). `validate.py` drops `#anchor` from links and checks no skill names or "workflow (Section)" references.
- **One record per doc type in `canon.py`** (R001-F12). A type's rules are spread over `TYPES`, `TEMPLATES`, the field tables, `check_doc`'s branches and the id helpers. Speculative.
- **Experiment bookkeeping** ([D008: Prototypes and research](../designs/D008-experiments.md), found in its as-built revision). Nothing fills an experiment's `modules`, and neither skill says who commits the experiment and its attachments, or when.
- **How strong a reviewer needs to be** (the user, 2026-11-12). Nothing shows how a reviewer's model and reasoning effort trade review quality against time: a same-model reviewer runs on the session's model and effort ([D003: Subagents](../designs/D003-subagents.md)), and the reviewer file orders cross-family reviewers by preference alone. Research and experiments that replay gates and code reviews with known findings at several models and efforts could set defaults that stay fast and still catch what matters; the snapshots and review dispositions of [D001: Skill telemetry](../designs/D001-skill-telemetry.md) could supply the cases.
- **Per-project trace and reviewer settings** (the user, 2026-11-13). Both are set once per user and machine. Tracing is on in every checkout once the machine switch exists, except one with its own `off` file ([D001§switch-and-storage: switch and storage](../designs/D001-skill-telemetry.md#switch-and-storage)), so piloting it in one project turns it on in all the others, and an `off` file covers one checkout, not the project's other clones and linked worktrees. Every checkout reads the one reviewer file ([D003§reviewers: reviewers](../designs/D003-subagents.md#reviewers)), so no project can use other cross-family reviewers or efforts than the rest, such as a work project limited to approved models. Settings per project, falling back to the machine's, would keep what the Decisions of both designs protect: they stay outside every checkout, so no commit turns tracing on for other users or carries a reviewer's tools and logins into the repository, and every clone and linked worktree of the project finds them. Revises D001 and D003.
- **Collecting canon's records across projects** (the user, 2026-11-13). Improving canon from real work means reading every project's records: trace events, archives and snapshots in each checkout's `.canon/canon/trace/` ([D001§switch-and-storage: switch and storage](../designs/D001-skill-telemetry.md#switch-and-storage)), and `canon-retro`'s `skills.jsonl` in `.canon/canon-retro/`, though that log records friction in canon, not in the project. On 2026-11-13 this machine held retro records in three projects and trace events in one, and nothing lists where they are. `canon-retro` writes into the checkout it runs in, so the records of a linked worktree in `.worktrees/` go when the worktree is removed, unlike its trace data; and the agent fills `skills.jsonl`'s version fields by hand, so three of this repository's four entries have `skill_hash: unknown`. A directory per user would gather them, but the Cursor and Codex sandboxes let agents write only inside the workspace, so every trace call would wait for approval unless each host allows that directory; snapshots borrow the project's objects; the analysis reads each project's docs and Git anyway; and other users' retros would pay the approval too. The likely shape keeps storage in the project and collects per user: `scripts/trace_report.py` finds every `.canon/canon/trace/` and `.canon/canon-retro/` under the roots it is given; a `canon.py` command appends a friction line, filling the date, host, session, model, canon version and the skill's digest ([D001§skill-digests: skill digests](../designs/D001-skill-telemetry.md#skill-digests)), whether tracing is on or off; and a linked worktree in `.worktrees/` writes its retro records to its main checkout, as it does its trace data. Decide once the pilot shows how often records are lost or hard to find. Revises D001.
- **Research and runs in `E` docs** (the user, 2026-11-12). Source research (`canon-research`) and runs (`canon-prototype`, benchmarks) stay in one doc type ([D006: Doc model and writing rules](../designs/D006-doc-model.md), [D008: Prototypes and research](../designs/D008-experiments.md)) while keeping separate execution skills: both answer one question with external evidence for designs and plans to cite, share the same status and link rules, and combine on one doc when a run follows research on the same question ([R003§r003-f18-a-research-experiment-later-measured: R003-F18](../archived/reviews/R003-silk-design-phase.md#r003-f18-a-research-experiment-later-measured)). D006 has no Decision stating why they share `E`, and three rough edges remain: the type directory `experiments/` reads narrowly for source research (where `E` acts as evidence); `canon.py new E` pre-fills `Commit:`, `Environment:` and `Command:`, which every research doc deletes to write `- Sources:`; and `terminal_problems` skips all three run labels whenever `Sources:` is filled, so a research doc that leaves empty template labels behind or gains a later run with missing run labels passes `check`.
- **Section paths** ([R001: Codebase review of the canon module](../archived/reviews/R001-canon-module.md), F1; the user, 2026-11-12). A `paths` entry could name part of a file, `file#section` by a Markdown heading or by a marker comment in code, so that `which`, `affected`, `Refs:` and coverage follow only the part a change touches. [D002§decisions: decisions](../designs/D002-overview-and-as-built.md#decisions) keeps whole files and says why; revisit when shared files make `Refs:` and the docs step's reading too costly.
- **Broad entries in any design's `paths`** (the user, 2026-11-12). `check` errors on a directory or glob in D000's `paths` only, because such an entry makes every file look governed and hides the gaps coverage reports ([D002§decisions: decisions](../designs/D002-overview-and-as-built.md#decisions)). Any other design can do the same with an entry covering a whole module, such as `skills/**`, `mod/` or `mod` (an entry also matches every path below a match), the natural choice for a module's own overview, and `which`, `affected`, `Refs:` and coverage then treat the whole module as specified. `check` could warn when a design's entry matches every file under a Modules Path of D000.
- **Code embedded in docs** ([R003§r003-f28-code-kept-twice: R003-F28](../archived/reviews/R003-silk-design-phase.md#r003-f28-code-kept-twice)). Canon cannot include a file in a doc, so a project copied attachment code into its docs with a script of its own and an `AGENTS.md` rule, and a session later edited a generated block by hand. A `canon.py embed` could write marked blocks from the files they show, with `check` failing a block that differs from its file and the line limit skipping generated blocks. A new topic: `/canon-design`.
- **Published experiment reports and external doc sites** (the user, 2026-11-12). An experiment answers one question ([D006§doc-types: doc types](../designs/D006-doc-model.md#doc-types)), and `check` restricts the top-level entries of `docs/` ([D006§layout: layout](../designs/D006-doc-model.md#layout)), so a web page that synthesizes data and conclusions across several experiments, such as for GitHub Pages, has no place inside `docs/`, while standalone evaluation experiments that feed no design or plan cannot reach `concluded` and show up as idle in `audit`. Keep `docs/` as the self-explanatory default engineering docs root and `docs/experiments/` as the source of truth, and publish pages as a derived view outside `docs/` (such as `site/` deployed by GitHub Actions, with a `README.md` linking the source `E` docs so `archive`, `rename` and `renumber` update its links), backed by a manual execution skill (e.g. `canon-report`); give answered experiments that feed no design or plan a clean end state; and when a project's root `docs/` already belongs to an external doc-site generator, let `init` ([D004§init: init](../designs/D004-project-setup.md#init)) record an alternate docs directory in the root `AGENTS.md` canon block.
- **Concurrent work, partial commits and staged or commit checks** ([R003§r003-f14-sessions-sharing-one-checkout: R003-F14](../archived/reviews/R003-silk-design-phase.md#r003-f14-sessions-sharing-one-checkout), [R003§r003-f34-checking-a-commit-or-the-staged-state: R003-F34](../archived/reviews/R003-silk-design-phase.md#r003-f34-checking-a-commit-or-the-staged-state), [R003§r003-f39-stale-index-as-an-error: R003-F39](../archived/reviews/R003-silk-design-phase.md#r003-f39-stale-index-as-an-error); the user, 2026-11-12). Ship R003-F14, F39 and F34 as one L2 change revising [D006: Doc model and writing rules](../designs/D006-doc-model.md), [D005: Docs index](../designs/D005-docs-index.md) and [D004: Project setup](../designs/D004-project-setup.md) together, with a plan. Parallel top-level sessions take a linked worktree and branch each (`.worktrees/<branch>`), since one checkout shares `.git/index`, review snapshots and worker stashes; in D004, `init` adds `.worktrees/` to `.gitignore` alongside `.canon/`, and `init --hook` runs `canon.py check --staged`, upgrading hooks that hold the plain `check` template. Within one checkout, for subagents restricted to their own files and for sessions splitting uncommitted work into separate commits: `canon.py check [ID|PATH...] [--fix]`, work-tree only and rejected with `--base`, checks and fixes frontmatter only on the named docs, checking links in their `.md` attachments and leaving indexes alone; `canon.py index --staged` regenerates index files in `.git/index` from the staged tree and writes work-tree expected indexes to disk when changed, since the work-tree index file already holds other uncommitted docs' lines; and `canon.py check --staged` and `canon.py check --rev <REV>` validate the staged index or a commit's tree through read-only Git queries, composable with `--base <REF>`, checking `updated` and deleted docs on non-merge commits with a parent against `<REV>^` and treating `<REV>`'s author or committer date as same-day for `updated`. In D005 and D006, `index out of date` becomes `WARN` in work-tree `check` and `ERROR` in `--staged`, `--rev` and `--base`, while unfinished docs and revisions pending review stay `WARN` in `--staged` and `--rev` and become `ERROR` only with `--base`.
- **Process findings wait for outside evidence** (a session's cost review, 2026-11-13). Gates on canon's own designs keep finding edge cases of canon's own bookkeeping, and each fix adds a conditional rule that the next gate probes: all four majors of the cross-family review in D007's revision 4 gate were such cases (a trace call site over its budget, an L2 approval nothing on disk records, the limits of a follow-up round, `status` transitions), and D006 took 15 revisions by 2026-11-13. Until a project outside this repository meets the same case, a finding about the process itself from this repository's gates and reviews lands here instead of becoming a rule; defects of `canon.py` are still fixed. Projects piloting canon turn tracing on ([D001: Skill telemetry](../designs/D001-skill-telemetry.md)) so that cost and failure data rank the ideas below. Adopted, it becomes a rule in `AGENTS.md`'s Workflow.
- **Code review scaled to risk** (a session's cost review, 2026-11-13). Every change, L0 included, gets Spec and Standards reviewers as fresh subagents ([D003§reviewers: reviewers](../designs/D003-subagents.md#reviewers)), so a typo fix or a dependency bump launches two subagents that read the governing designs, and a small L1 revision takes at least three with its gate ([D007§change-tiers: change tiers](../designs/D007-change-tiers.md#change-tiers)). An L0 change below a size or risk threshold could get one reviewer or a checklist, the Standards axis could run on a faster model (**How strong a reviewer needs to be** above), and an L1 revision of one section could pass one review of its design diff and code diff together. Wanted before wider rollout, since every change pays it.
- **One gate for a backfill and its change** (a session's cost review, 2026-11-13). A backfill passes an as-built revision through its own L1 gate and commits it alone, and the change's revision then passes another ([D002§backfill: backfill](../designs/D002-overview-and-as-built.md#backfill)). In a project with code and few designs most behavior changes take both, the friction most likely to stop a project with existing code from adopting canon. One gate whose prompt has an as-built part, pinned to the start commit so the review never checks the code against itself ([D002§decisions: decisions](../designs/D002-overview-and-as-built.md#decisions)), and a change part would keep what the split protects. Wanted before projects with existing code adopt canon.
- **Gate and review bookkeeping in `canon.py`** (a session's cost review, 2026-11-13). The `canon` skill says `canon.py` enforces every mechanical rule, yet the agent carries out from prose both Gate status ([D007§gate-status: gate status](../designs/D007-change-tiers.md#gate-status)), which sets `status`, `reviewed`, `reviewers`, `approved` and `implemented` across tiers, splits and as-built revisions, and the review files ([D003§review-snapshots: review snapshots](../designs/D003-subagents.md#review-snapshots), [D001§review-files: review files](../designs/D001-skill-telemetry.md#review-files)), with their round directories, snapshot and id files and the diff commands of confirmation and follow-up rounds. Commands such as `canon.py gate pass <ids> --tier <tier> --reviewers <ids>` and `canon.py review start|confirm|followup <topic>`, printing the snapshot, the filled prompt and the diff command, would shrink the text and the edge cases gates keep finding in it. Builds on **Work-tree snapshots apart from trace** above.
- **Instructions where their condition arises** (a session's cost review, 2026-11-13). Text that applies only under a condition is read every time: the `AGENTS.md` canon block, which every session reads, and the `canon` skill's Tool section both carry the full install commands, though `canon.py` detects when they apply ([D004§install: install](../designs/D004-project-setup.md#install)); and the texts an L0 change loads hold 14 `trace start` or `end` call sites that every session reads while tracing is off ([D001§call-sites: call sites](../designs/D001-skill-telemetry.md#call-sites)). Mechanical rules belong in `canon.py`, conditional ones in the output of the command that detects the condition, and only judgment in skill text: `canon.py` could print the install commands with the message that detects the need, and the trace calls could move into commands the workflows already run or into `trace.md`. Related: **One place for closing a workflow** above.
- **A token budget for the core texts** (a session's cost review, 2026-11-13). In `cl100k_base` tokens on 2026-11-13, the `canon` skill's `SKILL.md`, `workflow.md`, `doc-types.md` and `writing.md` held about 13,900; with `canon-implement`, `canon-tdd`, `canon-code-review` and `canon-blind-review` and the files they link, the texts an L0 change loads, about 23,000; all skill texts about 55,100; and `AGENTS.md` about 2,500. `validate.py` budgets only the trace text ([D001§budgets: budgets](../designs/D001-skill-telemetry.md#budgets)). Budgets for the core texts and the L0 path, measured by `validate.py`, would make each new rule displace or merge an old one.
- **Workers for small or independent slices** (a session's cost review, 2026-11-13). `canon-implement` builds every slice in a new worker, one at a time in plan order ([D003§launch: launch](../designs/D003-subagents.md#launch)), so a small slice pays for a worker that rereads the plan, the design sections and `canon-tdd` before a few lines of code, and independent slices wait for one another. The orchestrating session could build slices below a size itself, and slices with no dependency between them could run in parallel in linked worktrees (**Concurrent work, partial commits and staged or commit checks** above); [D001§units: units](../designs/D001-skill-telemetry.md#units) relies on one worker at a time to end a slice.

## Open questions

- Should a project's `AGENTS.md` without the canon block make the auto skills stand down entirely, or run their plain discipline without docs?
- What diff size or risk lets an L0 change, or an L1 revision of one section, take fewer reviewers, and which data from projects piloting canon settles it?
- What identifies a project across its clones and linked worktrees for per-project settings: its remote URL, its root commit, or an id the canon block records?
